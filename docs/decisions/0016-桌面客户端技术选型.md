# ADR-0016 VP 桌面客户端技术选型

**状态**: Accepted
**日期**: 2026-06-24
**作者**: Hermes (audit + 推荐) → 张胜东批准
**触发**: 用户原话 *"下一步做客户端吧"* + *"桌面客户端实现选哪个? 你自己定,但我觉得遇到问题还是要以解决问题为主,不要轻易退缩,要尽量采用最优方案"*

---

## 0. 上下文 — 为什么现在必须做

VPBuddy 真实主路径(2026-06-23 用户反复纠正,载入 vpbuddy-hermes-native skill):

| 抓音频方案 | 可行性 | 原因 |
|---|---|---|
| 浏览器 `getUserMedia` | ❌ | 只能麦克风,不能抓扬声器输出 |
| 浏览器 `getDisplayMedia` | ❌ | 只能抓当前标签页,腾讯/钉钉/企微客户端不在 |
| Bot 加入会议 (SDK) | ❌ | 3 套 SDK + 政企客户禁 bot |
| **OS 级 loopback (本地 Agent)** | ✅ | Linux PipeWire / Windows WASAPI / macOS CoreAudio |

**架构铁律(硬约束)**: VPBuddy 真主路径 = VP 桌面客户端跑本地 Agent → 推 GPU server。**不是 web 能做的事**。

当前现状:
- `scripts/install-client.sh` 73 行 — 只是 Linux 占位脚本,只检测 ffmpeg + pipewire
- `loopback.py` (Linux only) — PipeWire/PulseAudio 抓音频
- **没选定技术栈、没在 macOS/Windows 实测过、没真打包过**
- `vpbuddy-client/` 目录是 Tauri Rust 半成品骨架,`cargo build` 未跑通

## 1. 候选方案对比(三个维度,工程量从大到小)

### A. Electron + Node.js

| 维度 | 评估 |
|---|---|
| 包体积 | ❌ ~150MB(Chromium 内嵌) |
| 启动 | ~1.5s 冷启 |
| 音频抓取 | node-module `node-record-lpcm` (Linux/macOS OK, Windows 需 WASAPI 包装) |
| Web 技术栈 | ✅ TS/React/Vue 齐全, UI 迭代快 |
| 跨平台构建 | ✅ electron-builder 成熟 |
| 系统 tray | ✅ electron 自带 |
| 自启 | ✅ app.setLoginItemSettings |
| **用户已有经验** | ❓ 不确定 |

### B. Tauri 2.x + Rust(2025 stable)

| 维度 | 评估 |
|---|---|
| 包体积 | ✅ **~10MB**(用系统 WebView) |
| 启动 | ✅ ~0.4s 冷启 |
| 音频抓取 | `cpal` crate 跨平台 (Linux/macOS/Windows loopback) |
| Web 技术栈 | ✅ TS/React/Vue(复用现有 web UI 模板) |
| 跨平台构建 | ✅ tauri build 出 .deb/.dmg/.msi/.exe |
| 系统 tray | ✅ tauri-plugin-tray |
| 自启 | ✅ tauri-plugin-autostart |
| **学习曲线** | ⚠️ Rust + Tauri IPC(command/event) + 前端 TS 三层心智 |
| **用户已有经验** | vpbuddy-client/ 半成品 = 你或我之前开的 Tauri 坑 |

### C. Native Swift/Objective-C(macOS) + C#/WPF(Windows) + Rust/GTK(Linux)

| 维度 | 评估 |
|---|---|
| 包体积 | ✅ ~5MB/平台 |
| 启动 | ✅ < 0.3s |
| 音频抓取 | CoreAudio(完美) / WASAPI(完美) / PipeWire(可用) |
| Web 技术栈 | ❌ 没用 web,UI 用 SwiftUI/Catalyst/WPF 重写 |
| 跨平台构建 | ❌ **3 套独立工程** — 工作量 ×3 |
| **用户已有经验** | ❌ VPBuddy 没基础 |
| **YAGNI 视角** | ❌ 过度工程 |

---

## 2. 推荐方案 = **B. Tauri 2.x + Rust** + Python prototype 兜底

**理由**(按优先级):

1. **最小可工作产品 (MVP-YAGNI)** — 一个工程支持 3 平台,不需要 3 套独立开发
2. **音频抓取 `cpal` 跨平台已成熟** — 不需要自己写 WASAPI/CoreAudio/PipeWire 三个 wrapper
3. **复用 web UI 模板** — VPBuddy 现有 `ui/index.html` 4 窗口 shell **基本可复用**,只是从 server 静态目录搬进 Tauri webview
4. **包小** — 用户接受度高(150MB vs 10MB)
5. **已有半成品** — `vpbuddy-client/` 不用从零开始

**兜底**(应对"cargo build 卡"风险):
- **保留** `loopback.py` (Linux Python prototype) 作为 fallback
- **保留** `scripts/install-client.sh` — 用户 Linux 上能直接跑 Python prototype,不必等 Tauri build

## 3. 具体实施路径

### Phase A — Tauri 客户端骨架(目标:3 平台 build 跑通空白窗口)

```
vpbuddy-client/
├── src-tauri/
│   ├── Cargo.toml              # tauri 2.x + cpal + reqwest
│   ├── tauri.conf.json
│   ├── build.rs
│   └── src/
│       ├── main.rs             # Tauri 入口
│       ├── audio.rs            # cpal loopback 抓取
│       ├── stream.rs           # 30s 切片 + multipart POST
│       └── tray.rs             # 系统托盘
├── src/                        # 前端 TS (搬 vpbuddy/ui/index.html)
│   ├── main.ts
│   ├── app.ts
│   └── styles.css
├── package.json                # @tauri-apps/cli
├── tauri.conf.json
└── README.md
```

### Phase B — 音频流打通(目标:30s 切片推到 GPU server,UI 显示 6 docs 更新)

1. `cpal` 抓系统 loopback (按平台选 sink):
   - Linux: PipeWire monitor source
   - macOS: BlackHole 16ch 虚拟设备
   - Windows: WASAPI loopback
2. 30s 切片 → resample 到 16kHz mono → i16 PCM → WAV header
3. multipart POST `/api/meetings/{id}/stream_chunk`(端点已存在, commit eac6f58)

### Phase C — 体验完善(系统托盘 / 自启 / 设置页)

- `tauri-plugin-tray` — 托盘图标显示状态
- `tauri-plugin-autostart` — 开机启动
- 设置页填 GPU server URL + meeting_id prefix

## 4. 与现有架构的对接(零返工原则)

| 现有组件 | 客户端用不用 | 怎么用 |
|---|---|---|
| GPU server :8765 REST API | ✅ 全用 | 客户端只调 REST,不直连 DB |
| MeetingState JSON | ❌ 客户端不碰 | 服务端唯一真理 |
| 6 子 session | ❌ 客户端不碰 | 服务端触发,客户端只 GET 显示 |
| KB sqlite-vec | ❌ 客户端不碰 | 服务端检索,客户端看结果 |
| `loopback.py` (Python) | ✅ 保留 | Tauri 还没 build 完时,Linux 上跑 Python prototype |
| `stream_client.py` | ✅ 复用测试 | Tauri 联调前用它做协议验证 |

---

## 5. 风险与缓解

| 风险 | 缓解 |
|---|---|
| Tauri `cargo build` 几百 crate 慢(2026-06-23 已知坑) | Phase A 只跑 `cargo check`, 不真 build；联调时用 Python prototype + `stream_client.py` 推 |
| macOS CoreAudio 抓不到系统输出 | 需要装 BlackHole 虚拟声卡,在 README 写清楚(类似 Loopback 商业软件原理) |
| Windows WASAPI 权限 | 第一次需要用户授权"辅助功能/麦克风权限",in-app 引导 |
| 客户端配置丢失 | 设置存 `~/.config/vpbuddy-client/config.toml` |
| 网络断连 | 客户端本地 buffer 30s 音频 3 段,断网重传 |

---

## 6. 不做的事(防 YAGNI 滑坡)

- ❌ 不做本地 KB 同步 — 客户端是 thin client,知识库只在 GPU server
- ❌ 不做 P2P 多端协作 — 单 VP 单客户端,YAGNI
- ❌ 不做音频本地存档 — 服务端 MeetingState + 6 docs 够用,客户端不留副本
- ❌ 不做 Windows code signing — 内部使用,smoke test 后再说

---

## 7. 决策

**采用 B. Tauri 2.x + Rust**,保留 Python prototype (`loopback.py` + `stream_client.py`) 作为 Phase A 的兜底。Phase B 完成后 Tauri 是主路径,Python prototype 只在 Linux 开发环境应急用。

---

## 8. 验证(完工判据)

Phase A 完工 = `vpbuddy-client/` 在 3 平台(ubuntu/macos/windows) `cargo tauri build` 出 installer,空白窗口能开。
Phase B 完工 = 客户端 + GPU server 联调,真实会议 60s 采集 → 6 docs 自动更新 → 截图佐证。
Phase C 完工 = 系统托盘 + 自启 + 设置页三件套 commit。
