# 0010. 流式 E2E 端到端工作流 (stream chunk + long-lived AIAgent)

- **状态**: 已接受
- **日期**: 2026-06-23
- **作者**: 张胜东 (起草: Hermes)
- **替代**: 无
- **依赖**: [ADR-0006](./0006-MVP-Step3-子session架构.md) (5 doc + 1 demo agent), [ADR-0009](../0009-部署架构-Hermes-runtime.md) (Hermes runtime)

## 背景与问题

VPBuddy 之前 (commit `44a701a` 之前) 的"上传整文件 → 一次性处理"模式 (commit `05a2664` 实现) **只支持"会议结束后的回放"**, 不支持"正在开会时的实时入档". 张胜东 2026-06-23 明确要求:

> "应该一直采集并推送, gpu 服务也是一直在更新展示(6个?)和制作 demo 并显示"

需要的工作流:

1. VP 桌面客户端**持续**抓系统音频 (loopback) → 推 GPU server
2. GPU server **持续** funasr 增量转写 → 累加到 MeetingState
3. 5 doc agent + 1 demo agent **持续**读 state → 增量更新各自的输出文件
4. Web UI **持续**展示新文件 (时间线 / KB 检索 / demo iframe)

之前的实现 (commit `05a2664` + `eac6f58`):

- `POST /api/meetings/upload` (整文件) 仍工作 (回放场景)
- `subprocess.Popen("controller --once --meeting X")` 每次**新进程** (跨进程 agent cache 丢失)
- demo agent 跟其他 5 doc agent **混在一起** (张胜东纠正: demo 单独拎出来)
- 没有"会议开始 = GPU 端自动起 AIAgent session"的入口

## 考虑的选项

### 选项 A — 保留 `--once` 触发, 不改架构
- 优点: 零代码风险
- 缺点: 跟 ADR-0009 "用 in-process AIAgent 长驻"完全矛盾; 每次触发 `_AGENT_CACHE` 丢, LLM 上下文不连续

### 选项 B — `subprocess.Popen` 改成 `subprocess.Popen("controller --main-loop --meeting X")`
- 优点: 进程常驻, agent cache 在 controller 进程内
- 缺点: 跨进程通信 (state 改了 controller 怎么知道) + 资源占用 (每个会议一个 controller 进程)

### 选项 C — in-process AIAgent 触发, UI 进程内 6 agent 真长驻 ✅ (本次落地)
- 优点: 跟 ADR-0009 完全对齐; 跨 chunk 同一 session_id 复用; 资源占用低
- 缺点: UI 进程负担 6 个 LLM 调 (但 in-process + ThreadPoolExecutor 真并行, 实际可接受)

## 决策

**采用选项 C**。理由:

1. ADR-0009 + ADR-0006 明文要求 "in-process AIAgent session_id 复用"
2. UI 进程已经是 controller 的客户端 (它读 `data/meetings/` 写 docs), 集成触发逻辑**无新依赖**
3. `ThreadPoolExecutor(max_workers=3)` 6 个 sub_session 真并行 (3 并发避免 LLM rate limit)

### 落地架构

```
VP 客户端 (loopback, 30s WAV chunk)
   ↓ multipart POST /api/meetings/{id}/stream_chunk
GPU UI server (8765)
   ↓ funasr 增量转写
   ↓ load 已有 state + append new segments
   ↓ ThreadPoolExecutor(3) 调 6 个 trigger_sub_session
       ↓  (req/arch/tasks/api/risk/demo) × AIAgent (cached by session_id)
       ↓  in-process AIAgent.chat() (跨 chunk 复用同一 instance)
       ↓  write_file → docs/{mid}/{kind}.{md|html}
       ↓  KB add_document → sqlite-vec
   ↓ fire-and-forget (不阻塞 HTTP 响应)
```

**新端点** (commit `eac6f58`):
- `POST /api/meetings/stream_start` — 创建空 state, 返回 meeting_id
- `POST /api/meetings/{id}/stream_chunk` — multipart WAV → funasr → append state → trigger 6 agent in-process

**5 doc agent + 1 demo agent** (2026-06-23 张胜东纠正):
- 5 doc agent (req/arch/tasks/api/risk) 写 .md
- **demo agent 单独拎出来** (不在 5 里面), 写 demo/demo.html
- 6 个 agent **toolsets 都一样** `["terminal", "file"]` (2026-06-23 张胜东二次纠正: 不要 sandbox 禁止 fetch/eval, 先看效果)
- 不同会议 = 不同 AIAgent 实例 (上下文隔离)
- 同一会议内, 跨 chunk = 同一 AIAgent 实例 (LLM 跨次记得上下文)

**demo agent 输出约束** (在 prompt 强制, 不在 toolset 限制):
- 单文件 (只 demo.html)
- inline CSS/JS (无外部 <link>/<script src="http...">)
- 真可交互 (按钮响应 / 表单 / 列表过滤)
- 真实模拟数据 (类似产品说明书, 不用 Item 1/2/3)
- 浏览器层 sandbox: Web UI 用 `<iframe sandbox="allow-scripts">` 渲染

**Hermes 集成**:
- VPBuddy 装成 hermes skill: `~/.hermes/skills/vpbuddy/SKILL.md` (5 doc + 1 demo 描述)
- `from run_agent import AIAgent(session_id="meeting:{mid}:{kind}")` 跨调用复用
- controller 30s 轮询**降级为 fallback** (紧急恢复), **新常态是 in-process event-driven 触发**

## 客户端 → GPU 协议

`stream_chunk` 请求 (multipart/form-data):
- field `audio` = 30s mono 16kHz WAV
- 必填: `meeting_id` 已在 URL path
- 可选但桌面客户端应发送:
  - `chunk_index`: 从 0 开始递增,服务端用于识别重复上传
  - `chunk_start_sec`: 当前 chunk 在会议中的绝对起点秒数
  - `overlap_sec`: 客户端切片保留的重叠秒数,当前实现为 2s
  - `client_sent_at`: 客户端上传时的 Unix 时间戳,服务端用于计算端到端延迟

`stream_chunk` 响应 (JSON):
```json
{
  "meeting_id": "STREAM_20260624_...",
  "chunk_index": 0,
  "new_segments": [{"start_sec": 0.5, "end_sec": 4.2, "text": "...", "speaker_id": "SPEAKER_01", "chunk_index": 0}, ...],
  "state_items": {"requirements": 2, "goals": 0, "features": 0, "risks": 0, "questions": 0},
  "metrics": {"processing_ms": 1200, "end_to_end_ms": 1600, "raw_segments": 2, "new_segments": 2},
  "docs_triggered": true
}
```

### 当前实时推送协议

客户端连接 `GET /api/meetings/{meeting_id}/events` 接收 SSE。服务端当前会推送这些事件:

- `connected`: SSE 已连接
- `transcript-segment`: 新转写片段
- `state-update`: 结构化事实统计和最近事实列表
- `metrics-update`: chunk 处理耗时、端到端延迟、新增片段数
- `doc-update`: 6 类文档触发、生成完成、正文回流和 Demo HTML 回流
- `heartbeat`: 长连接保活

服务端维护内存事件历史,客户端重连时可通过 `Last-Event-ID` header 或 `?last_event_id=` 查询参数补收最近事件。该历史不是永久存储,进程重启后会丢失。

### 当前服务端 API

- `POST /api/meetings/stream_start`: 创建流式会议和空 MeetingState
- `POST /api/meetings/{id}/stream_chunk`: 接收 WAV chunk,转写、入 state、触发 6 类文档和 SSE 推送
- `GET /api/meetings/{id}/events`: SSE 事件流
- `GET /api/meetings/{id}/state`: 返回 MeetingState、转写历史、处理指标和已处理 chunk
- `GET /api/meetings/{id}/docs`: 返回 6 类文档正文,其中 Demo 为 `demo/demo.html`
- `GET /api/meetings/{id}/docs/{kind}`: 返回单个文档正文

### 当前代码边界

桌面客户端和服务端的职责边界已经固定:

- 桌面客户端负责采集音频、切 30s chunk、保留 2s overlap、上传服务端、连接 SSE、展示事实/文档/Demo。
- 服务端负责 ASR、说话人映射、事实抽取、6 类文档生成、Demo 生成、KB 入库和 SSE 推送。
- AI 可以主动把候选结论、风险和文档状态推给 VPBuddy 客户端,但不能主动外发给客户、外部系统或会议投屏。
- 投屏属于会议软件职责,VPBuddy 只在客户端内展示。
- 6 类交付物固定为 `req`、`arch`、`tasks`、`api`、`risk`、`demo`,UI 和测试不得随意增减。

当前实现还包含这些工程约束:

- `realtime_server.py` 的 SSE pub/sub 和事件历史是进程内内存结构,不是跨进程消息队列。
- `stream meta` 持久化在 `{DATA_DIR}/{meeting_id}.stream.json`,包含已处理 chunk、转写历史和处理指标。
- 重复 chunk 通过 `chunk_index` 拦截;重复片段通过最近转写文本做轻量去重,不是语义级去重。
- `speaker_map` 在同一会议内保持稳定,新 speaker 只补新增映射,避免跨 chunk 漂移。
- 文档生成完成后会把正文推到 SSE,Demo 以 HTML 字符串回流,客户端用 iframe 预览。
- KB 入库仍是后台线程,失败会重试,不阻塞 `stream_chunk` 响应。

**⚠️ 关键修复** (commit `eac6f58`):
- Python client `wav_chunk_bytes()` 必须先 `* 32767` 再 `astype(int16)`, 直接 astype 会把 [-0.61, 0.75] 截成 0/-1 = 全部静音
- funasr VAD 在 30s 全静默时会**返 0 segments**, 不要误判 ASR 失败 (正常)

## 端到端测试口径

现在有两类端到端测试,结论不同,不能混用:

### 进程内测试

命令:

```bash
PYTHONPATH=src python src/tests/test_e2e_realtime_standalone.py
```

该测试在同一 Python 进程内启动 UI server 线程,覆盖 SSE 端点、多客户端订阅、会议隔离、历史补偿、状态 API、文档 API、chunk 元数据和去重。它适合快速回归服务端实时链路。

### 两进程无头测试

服务端进程:

```bash
PYTHONPATH=src python src/tests/headless_test_server.py --host 127.0.0.1 --port 18767
```

客户端进程:

```bash
PYTHONPATH=src python src/tests/headless_client.py --server http://127.0.0.1:18767 --chunks 1 --json
```

该测试更接近真实部署:一个进程跑服务端,另一个进程跑客户端,通过真实 HTTP/SSE 完成 `stream_start`、`stream_chunk`、`state`、`docs` 和事件回流。测试服务端会安装 fake ASR 和 fake 文档生成器,因此它验证的是协议和实时链路,不验证真实 funasr、真实 LLM、Hermes、GPU 或 Tauri GUI。

### 真实环境验证

要验证真实 ASR/LLM 环境,把服务端换成真实 `vpbuddy.ui_server` 或生产启动脚本,再运行同一个 `headless_client.py`。这时需要满足:

- funasr 及 GPU/CPU 推理依赖可用
- Hermes 或 fallback 文档生成路径可用
- `VPBUDDY_DATA_DIR`、`VPBUDDY_DOCS_DIR`、`VPBUDDY_KB_DB` 指向可写目录
- 如果构建 Tauri 桌面客户端,Linux 环境需安装 GTK/WebKit/GLib 开发库;当前沙箱缺少 `glib-2.0.pc`,所以 `cargo check` 会在 `glib-sys` 处被系统依赖阻断

## 已知限制

1. funasr 仍是 batch chunk 模式,不是 token/帧级 streaming ASR。客户端通过 30s chunk + 2s overlap 降低截断风险,但实时性仍受 chunk 长度和 ASR 推理耗时影响。
2. SSE 事件历史是进程内内存,服务端重启后无法补发重启前事件。`MeetingState`、stream meta 和 docs 会落盘,但 SSE event log 没有持久化。
3. 6 agent 跨 chunk 复用依赖服务端进程常驻。如果服务端崩溃重启,`_AGENT_CACHE` 丢失,文档可从已有文件继续生成,但 LLM 内存上下文不保证连续。
4. 无头两进程测试使用 fake ASR/文档生成器,不能代表真实模型质量、真实 GPU 性能或真实 LLM 输出质量。
5. Tauri GUI 构建依赖系统 GTK/WebKit/GLib 开发库。缺少这些系统包时,Rust 代码可能无法完整 `cargo check`,即使服务端和无头客户端链路已经通过。
6. 当前事实分类仍是启发式规则,`REQ/GOAL/FEAT/RISK/QUE` 的准确率需要真实会议语料继续校准。
7. Demo iframe 预览只在客户端内部展示,不会自动外发或投屏。
