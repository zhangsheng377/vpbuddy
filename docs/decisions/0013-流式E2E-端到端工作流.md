# 0010. 流式 E2E 端到端工作流 (stream chunk + long-lived AIAgent)

- **状态**: 已接受
- **日期**: 2026-06-23
- **作者**: 张胜东 (起草: Hermes)
- **替代**: 无
- **依赖**: [ADR-0006](./0006-MVP-Step3-子session架构.md) (5 doc + 1 demo agent), [ADR-0009](../0009-部署架构-Hermes-runtime.md) (Hermes runtime)

## 背景与问题

VPBuddy 之前 (commit `44a701a` 之前) 的"上传整文件 → 一次性处理"模式 (commit `05a2664` 实现) **只支持"会议结束后的回放"**, 不支持"正在开会时的实时入档". 张胜东 2026-06-23 明确要求:

> "应该一直采集并推送, gpu 服务也是一直在更新展示(6个?)和制作 demo 并显示"

需要的工作流:

1. VP 桌面客户端**持续**抓系统音频 (loopback) → 推 GPU server
2. GPU server **持续** funasr 增量转写 → 累加到 MeetingState
3. 5 doc agent + 1 demo agent **持续**读 state → 增量更新各自的输出文件
4. Web UI **持续**展示新文件 (时间线 / KB 检索 / demo iframe)

之前的实现 (commit `05a2664` + `eac6f58`):

- `POST /api/meetings/upload` (整文件) 仍工作 (回放场景)
- `subprocess.Popen("controller --once --meeting X")` 每次**新进程** (跨进程 agent cache 丢失)
- demo agent 跟其他 5 doc agent **混在一起** (张胜东纠正: demo 单独拎出来)
- 没有"会议开始 = GPU 端自动起 AIAgent session"的入口

## 考虑的选项

### 选项 A — 保留 `--once` 触发, 不改架构
- 优点: 零代码风险
- 缺点: 跟 ADR-0009 "用 in-process AIAgent 长驻"完全矛盾; 每次触发 `_AGENT_CACHE` 丢, LLM 上下文不连续

### 选项 B — `subprocess.Popen` 改成 `subprocess.Popen("controller --main-loop --meeting X")`
- 优点: 进程常驻, agent cache 在 controller 进程内
- 缺点: 跨进程通信 (state 改了 controller 怎么知道) + 资源占用 (每个会议一个 controller 进程)

### 选项 C — in-process AIAgent 触发, UI 进程内 6 agent 真长驻 ✅ (本次落地)
- 优点: 跟 ADR-0009 完全对齐; 跨 chunk 同一 session_id 复用; 资源占用低
- 缺点: UI 进程负担 6 个 LLM 调 (但 in-process + ThreadPoolExecutor 真并行, 实际可接受)

## 决策

**采用选项 C**。理由:

1. ADR-0009 + ADR-0006 明文要求 "in-process AIAgent session_id 复用"
2. UI 进程已经是 controller 的客户端 (它读 `data/meetings/` 写 docs), 集成触发逻辑**无新依赖**
3. `ThreadPoolExecutor(max_workers=3)` 6 个 sub_session 真并行 (3 并发避免 LLM rate limit)

### 落地架构

```
VP 客户端 (loopback, 30s WAV chunk)
   ↓ multipart POST /api/meetings/{id}/stream_chunk
GPU UI server (8765)
   ↓ funasr 增量转写
   ↓ load 已有 state + append new segments
   ↓ ThreadPoolExecutor(3) 调 6 个 trigger_sub_session
       ↓  (req/arch/tasks/api/risk/demo) × AIAgent (cached by session_id)
       ↓  in-process AIAgent.chat() (跨 chunk 复用同一 instance)
       ↓  write_file → docs/{mid}/{kind}.{md|html}
       ↓  KB add_document → sqlite-vec
   ↓ fire-and-forget (不阻塞 HTTP 响应)
```

**新端点** (commit `eac6f58`):
- `POST /api/meetings/stream_start` — 创建空 state, 返回 meeting_id
- `POST /api/meetings/{id}/stream_chunk` — multipart WAV → funasr → append state → trigger 6 agent in-process

**5 doc agent + 1 demo agent** (2026-06-23 张胜东纠正):
- 5 doc agent (req/arch/tasks/api/risk) 写 .md
- **demo agent 单独拎出来** (不在 5 里面), 写 demo/demo.html
- 6 个 agent **toolsets 都一样** `["terminal", "file"]` (2026-06-23 张胜东二次纠正: 不要 sandbox 禁止 fetch/eval, 先看效果)
- 不同会议 = 不同 AIAgent 实例 (上下文隔离)
- 同一会议内, 跨 chunk = 同一 AIAgent 实例 (LLM 跨次记得上下文)

**demo agent 输出约束** (在 prompt 强制, 不在 toolset 限制):
- 单文件 (只 demo.html)
- inline CSS/JS (无外部 <link>/<script src="http...">)
- 真可交互 (按钮响应 / 表单 / 列表过滤)
- 真实模拟数据 (类似产品说明书, 不用 Item 1/2/3)
- 浏览器层 sandbox: Web UI 用 `<iframe sandbox="allow-scripts">` 渲染

**Hermes 集成**:
- VPBuddy 装成 hermes skill: `~/.hermes/skills/vpbuddy/SKILL.md` (5 doc + 1 demo 描述)
- `from run_agent import AIAgent(session_id="meeting:{mid}:{kind}")` 跨调用复用
- controller 30s 轮询**降级为 fallback** (紧急恢复), **新常态是 in-process event-driven 触发**

## 客户端 → GPU 协议

`stream_chunk` 请求 (multipart/form-data):
- field `audio` = 30s mono 16kHz WAV
- 必填: `meeting_id` 已在 URL path

`stream_chunk` 响应 (JSON):
```json
{
  "meeting_id": "STREAM_20260624_...",
  "new_segments": [{"start_sec": 0.5, "end_sec": 4.2, "text": "...", "speaker_id": "SPEAKER_01"}, ...],
  "state_items": {"requirements": 0, "risks": 0, "questions": 2},
  "docs_triggered": true
}
```

**⚠️ 关键修复** (commit `eac6f58`):
- Python client `wav_chunk_bytes()` 必须先 `* 32767` 再 `astype(int16)`, 直接 astype 会把 [-0.61, 0.75] 截成 0/-1 = 全部静音
- funasr VAD 在 30s 全静默时会**返 0 segments**, 不要误判 ASR 失败 (正常)

## 已知限制

1. **funasr 是 batch 模式** (整 30s 一起转, 15s 跑完), 不是真 streaming VAD. latency 仍是 15s. 真 streaming 需要换 `AutoModel.generate()` 流式 input, 留给 VP 客户端用户体验优化阶段
2. **6 agent 跨 chunk 复用**依赖 UI 进程常驻, 如果 UI 崩了重启, `_AGENT_CACHE` 丢, 6 个 agent 重新起 (LLM 上下文断). production 应该把 agent 状态持久化到 `~/.hermes/sessions.db` (hermes 原生支持)
3. **Web UI 没加 SSE 实时推** (doc 状态 / 新 segment 推送), 仍用 30s 轮询 `GET /api/timeline`. SSE 留作 UI 增强
