## 1. pyannote 3.3.2 + huggingface_hub 1.20.1 不兼容

### 现象
```
TypeError: hf_hub_download() got an unexpected keyword argument 'use_auth_token'
```

### 原因
- `pyannote-audio 3.3.2` 用旧的 `use_auth_token=...` 调用
- `huggingface_hub 1.20+` 已弃用该参数,改名 `token=...`
- pyannote 还没适配新版 HF

### 解决方案 (3 选 1)

**方案 A: monkeypatch** (已用,推荐,最简单)
```python
import huggingface_hub
_orig = huggingface_hub.hf_hub_download
def patched(*args, **kwargs):
    if "use_auth_token" in kwargs:
        kwargs["token"] = kwargs.pop("use_auth_token")
    return _orig(*args, **kwargs)
huggingface_hub.hf_hub_download = patched
```

**方案 B: 降级 huggingface_hub**
```bash
pip install "huggingface_hub<1.0"
```
不推荐,会引出别的兼容问题。

**方案 C: 升级 pyannote**
等官方修。

## 2. pyannote Pipeline.from_pretrained 不接受绝对路径

### 现象
```
HFValidationError: Repo id must be in the form 'repo_name' or 'namespace/repo_name': '/tmp/...'
```

### 原因
- pyannote 3.x 用 `hf_hub_download` 解析路径,只接受 `org/repo` 格式
- 旧版能接受本地路径

### 解决方案: 手工建 HF cache 布局

pyannote 内部走 `hf_hub_download(repo, ...)` 时会找:
```
~/.cache/huggingface/hub/models--{org}--{repo}/
├── refs/main           (内容: "main" 或 commit SHA)
└── snapshots/main/{files}
```

**注意**:必须有 `refs/main` 文件 + `snapshots/main/` 目录,但**不需要 `blobs/`**(HF 自己会用)。

```bash
# 1. 把本地模型放到 ~/.cache/vpbuddy_models/pyannote/segmentation-3.0/
# 2. 建 HF cache layout
mkdir -p ~/.cache/huggingface/hub/models--pyannote--segmentation-3.0/{refs,snapshots/main}
echo "main" > ~/.cache/huggingface/hub/models--pyannote--segmentation-3.0/refs/main
cp -r ~/.cache/vpbuddy_models/pyannote/segmentation-3.0/* \
      ~/.cache/huggingface/hub/models--pyannote--segmentation-3.0/snapshots/main/
```

然后调用:
```python
from pyannote.audio import Pipeline
pipeline = Pipeline.from_pretrained(
    "pyannote/segmentation-3.0",
    cache_dir="/home/zsd/.cache/huggingface/hub",
)
```

## 3. pyannote config.yaml 内嵌相对路径

### 现象
加载完 pipeline 后,又报 `LocalEntryNotFoundError` 找不到子模型。

### 原因
`config.yaml` 里写:
```yaml
pipeline:
  params:
    segmentation: pyannote/segmentation-3.0
    embedding: pyannote/wespeaker-voxceleb-resnet34-LM
```

pyannote 会用 `hf_hub_download("pyannote/segmentation-3.0", "pytorch_model.bin", ...)`。
如果在 `snapshots/main/pytorch_model.bin` 不存在,就报错。

### 解决方案
确保 `snapshots/main/` 下有所有 config 引用到的文件(.bin / .pt / .yaml 等)。

## 4. Pipeline.from_pretrained 传本地 config 文件路径

### 现象
传绝对路径不行(`HFValidationError`),但传相对路径可能可以。

### 解决方案
```python
CONFIG_FILE = "/home/zsd/.cache/huggingface/hub/models--pyannote--speaker-diarization-3.1/snapshots/main/config.yaml"
```

## 5. funasr SenseVoice 只输出 1 个 segment

### 现象
```python
result = model.generate(input=audio, fs=16000)
print(len(result))  # 1,而不是按句切分的多段
```

### 原因
默认 SenseVoice 不带 VAD/punc/spk,输出整个文本当一段。

### 解决方案: 加 VAD + punc + spk
```python
model = AutoModel(
    model="iic/SenseVoiceSmall",
    vad_model="iic/speech_fsmn_vad_zh-cn-16k-common-pytorch",
    punc_model="iic/punc_ct-transformer_zh-cn-common-vocab272727-pytorch",
    spk_model="iic/speech_campplus_sv_zh-cn_16k-common",
    device="cuda",
)
result = model.generate(input=audio, fs=16000, batch_size_s=60)
# 现在 result[0]["sentence_info"] 是 [{start, end, text, spk}, ...] 列表
```

## 6. sentence_timestamp=True 与 punc/spk 冲突

### 现象
```python
result = model.generate(input=audio, fs=sr, sentence_timestamp=True)
# KeyError: 'timestamp'
```

### 原因
funasr 1.3.11 在 sentence_timestamp=True 时走不同代码路径,跟 punc + spk 组合触发 bug。

### 解决方案
**不传 `sentence_timestamp=True`**,改用 VAD + punc + spk 默认输出:
```python
result = model.generate(input=audio, fs=sr, batch_size_s=60)
# result[0]["sentence_info"] = [{start, end, sentence, spk}, ...]
```

## 12. Hermes sub-session 触发没 file 工具 = SILENT FAILURE

### 现象
`controller.py` 调 `hermes chat -q "..."` 触发新 session 跑 sub-agent,
所有 sub-agent 都返回 `triggered=True err=None`,但**磁盘上一个文件都没写**。

### 原因
`hermes chat -q` 启动的新 session **不加载 file 工具**(只读 LLM 调用),
`write_file` / `patch` 调用全部静默失败,exit 0 假装成功。

### 解决方案
**`VPBUDDY_DIRECT=1` 模式**(commit `1087313`):controller 直接返回 `{prompt, doc_path}`,
**主 session 自己写文件**。绝不调 hermes sub-session 写文件。

```python
if os.environ.get("VPBUDDY_DIRECT") == "1":
    return {"mode": "direct", "prompt": ..., "doc_path": ..., "triggered": True}
```

## 13. GitHub push TLS 断连 + token 误判死(2026-06-21)

### 现象
- `git push origin main` 失败 `GnuTLS recv error (-110): TLS non-properly terminated`
- `gh auth setup-git` 后 3 次 push 都 `Authentication failed`

### 真实原因(误判)
1. **江苏联通 GFW 随机阻 git 协议**(走 443 但探测 git-specific payload)
2. **token 实际一直活着**,`~/.config/gh/hosts.yml` 里 `ghp_xxx` 是**完整 36 字符明文**
3. **我自己 mask 了 token**(`ghp_q2...hQLf`)给用户看,误以为是死 token,误判 30 分钟

### 诊断铁律(顺序!)
```bash
# 1. 先 curl /user,看 token 真活没
TOKEN=$(grep oauth_token ~/.config/gh/hosts.yml | head -1 | awk '{print $2}')
curl -H "Authorization: token $TOKEN" https://api.github.com/user
# → login: zhangsheng377 = 活

# 2. 再 curl repo
curl -o /dev/null -w "%{http_code}" -H "Authorization: token $TOKEN" \
  https://api.github.com/repos/zhangsheng377/vpbuddy
# → 200 = scope 够

# 3. 最后判 push 失败是 GFW 不是 token
```

### Fallback 顺序
1. `git push` 失败 → 等 30-60s 重试 3 次
2. 还失败 → **`gh api -X PUT` 逐文件 PUT**(接受 N 个 commit)
3. 留 force push 明天 squash

```bash
gh api -X PUT repos/zhangsheng377/vpbuddy/contents/PATH \
  --input <(jq -n --arg c "$(base64 -w0 FILE)" \
    '{message:"...", content:$c, sha:"<现有SHA 或 null>"}')
```

VPBuddy 5 文件全 PUT 成功: `origin/main = 6d63a10e`(5 个 PUT commit,可接受)。

4. **faster-whisper 重下**: hf 镜像 → `~/huggingface/hub/models--Systran--faster-whisper-large-v3/`
   - **关键**: 第一次下到 `snapshots/main/` 不行,hf_hub 找 `snapshots/<commit_hash>/`

- pip download.pytorch.org `cu121` 镜像 **通的**(慢但能下)
- conda 清华镜像有 pytorch 包(也通的)
- "装不上"是之前默认 `--timeout 100` 太短 + 之前 SSH 后台进程没杀干净(300s timeout 杀掉本地 Python,但 SSH 端 pip 还活着)

- `pip install download.pytorch.org` 用 **`--timeout 900`**(不是默认 100)
- 模型用 `hf download`(自动建 commit_hash)而不是 `hf download --local-dir .../snapshots/main`
- 杀后台 pip 用 `kill -9 <pid>` 直接对 GPU 端 process,SSH timeout 杀不到

### §18 VPBuddy 部署 = Hermes runtime,不是独立 Python 包 (2026-06-21 ADR-0009)

**背景**: 之前 VPBuddy 是"独立 Python 包 + 自己管 LLM/session/skill/memory",部署到新服务器 = `git clone` + `pip install -r requirements.txt`。问题:不重不重,完全重造 Hermes 已有的 4 套轮子。

**坑**:
1. 部署文档 (`gpu服务器部署.md`) 旧版**完全没提安装 Hermes** — 只写怎么装 GPU 模型,操作员装完一脸懵
2. 文档说"VPBuddy 不直接调 LLM,都用 Hermes",但 `pyproject.toml` 完全没有 `hermes-agent` 依赖 — 文档与代码 drift
3. `controller.py` 手编 5 Agent 循环 (`asyncio.gather`),没用 Hermes `delegate_task` 真并行 — 丢真并行能力
4. `src/vpbuddy/__init__.py` 注释写"运行在 Hermes Agent 之上",但 `import hermes` 0 命中 — 文档与代码 drift

**真相** (ADR-0009):
- VPBuddy = **装在 `~/.hermes/skills/vpbuddy/` 的 skill 集合**,**不是独立 Python 包**
- 一次会议 = 一个 Hermes session
- 5 Agent 并行 = Hermes `delegate_task(tasks=[...5])` 真并行 (ThreadPoolExecutor max_workers=3)
- 部署到新服务器 = `pip install hermes-agent` + `pip install vpbuddy` + `hermes skills install vpbuddy` (5 分钟起)
- 所有 LLM/session/skill/memory 委托 Hermes,VPBuddy 只做"会议应用层"

**教训**:
- **架构认知要先写 ADR** — 之前 v1.7 在总体架构 §0 写过"VPBuddy = Hermes skill 集合",但**没独立 ADR**,导致工程层完全没落地
- **文档与代码必须同步** — 文档说"用 Hermes",代码就要 `import hermes_tools`,否则就是骗自己
- **依赖要声明** — `pyproject.toml` 必须有 `hermes-agent>=0.16.0,<1.0`,否则装 VPBuddy 不装 Hermes,跑不起来
- **部署文档要真测** — "5 分钟起"得真测过,不能写文档的人云亦云

### §19 sentence-transformers 反复 HEAD HF endpoint,GPU pytest 卡 53min (2026-06-22)

**坑**:
- 跑 GPU pytest 完整 78 个,卡 53 分钟不报失败,只显示 `test_knowledge_base.py .` 第一个 dot
- `ss -tnp | grep pytest` 显示 1 个 TCP SYN-SENT 到 `69.63.186.30:443` (Facebook AS32934) + `2a03:2880:...:443`
- `py-spy dump` 看 stack:`SentenceTransformer.__init__ → load_file_path → hf_hub_download → http_backoff → _validate_conn → connect` 卡在网络请求

**真相**:
- `69.63.186.0/24` 和 `2a03:2880::/32` 是 **Meta (Facebook) 的 AS32934 IP 段**,但被 **facebookresearch**(sentence-transformers 母公司)等多个研究机构复用为 HuggingFace CDN 节点(虽然 ipinfo 显示 AS32934,但实际承载 HF endpoint)

## 15. Vision 识图 401 — Hermes 路由到 OpenRouter (2026-07-12)

### 现象

用户上传图片到 VP Chat 后，Hermes vision 工具链返回 `401 Unauthorized`：
- Hermes 内部用 MiniMax API key 打 `api.anthropic.com` → 401
- DashScope 端点不支持 Anthropic messages 协议 → 404

### 根因

三条线索叠加：
1. **`/etc/environment` 残留** `OPENROUTER_API_KEY` → Hermes 启动时自动吸入 `auth.json` 凭据池
2. **Hermes 硬编码常量** `OPENROUTER_BASE_URL = "https://openrouter.ai/api/v1"` → 当 `config.yaml` 缺 `model.base_url` 时，URL 回退链永远落到 OpenRouter
3. **`sub_session_controller.py` 猴子补丁只打了一处** → 主 chat agent (`_get_chat_agent`) 漏掉了

### 修复方案 (ADR-0054)

三层逃生通道：

### 三层防护的改动清单

| 文件 | 改动 |
|------|------|

## 16. `parent_session_id` fork 不生效 — 子 agent 收不到 chat 历史 (ADR-0055, 2026-07-13)

### 现象

用户反馈：在 VP Chat 里上传的图片、讨论的需求变更，batch_docs 和 demo 子 agent 毫不知情。ADR-0041 设计文档声称 `AIAgent(parent_session_id=...)` 会使子 agent 继承父 session 全部对话历史。

### 根因

阅读 Hermes 源码确认：
- `parent_session_id` 在 `run_agent.py:531-539` 存入 SQLite `sessions.parent_session_id` 列
- `turn_context.py:L259` 对话循环入口：`messages = list(conversation_history) if conversation_history else []` — `conversation_history` 参数始终为 `None`
- `conversation_loop.py` / `turn_context.py` 全文无 `parent_session_id` 引用

**`parent_session_id` 仅作 DB 血缘标记，对​话循环全程不读。** 子 agent 启动时消息历史从 `[]` 开始。

### 修复

在 VPBuddy 应用层手动注入 chat 历史到 `format_state_summary()`：
- 读取 `{mid}.chat.json`，格式化最近 20 条对话
- 超长内容截断，但暴露完整 JSON 文件路径
- 子 agent 可用 `read_file` 读取全量历史
- 上传文件列表同样在 prompt 中列出

### 教训

1. **不要在文档里假设框架功能** — ADR-0041 声明 "parent_session_id fork 继承全部历史"，但从未端到端验证
2. **阅读框架源码再写 ADR** — 应该在写 ADR-0041 之前就先 grep Hermes 源码确认 `conversation_loop` 是否真的消费 `parent_session_id`
3. **应用层兜底总是可行的** — 即使框架不支持，手动读 JSON 注入 prompt 也能达到同样效果，代价只是 prompt 长度增加

## §17 百炼 idle timeout 导致客户端断连 (2026-07-14)

### 现象
用户在会议中长时间不说话（>10s），客户端突然显示"未连接"/"recording-disconnected"，无法收到后续文档生成结果，需要手动重连。

### 根因
阿里云百炼 Fun-ASR-Realtime 服务端有 idle timeout（约 10-20 秒无有效语音即关闭 WebSocket）。百炼一关，`send_audio()` 在底层的 `recognition.send_audio_frame()` 调用抛出异常，导致 WS handler loop `break` 退出 → 客户端 WS 断开 → SSE 推 `recording-disconnected`。

注意：这不是网络问题，也不是客户端代码问题——是百炼自身的设计行为。

### 修复 (v0.22.8, commit 34b02f7/582bc38, 3 files)
1. `bailian_asr.py`: 新增 `_ASRSession.needs_reconnect` 标志位 + `restart_session()` 函数，在 `on_close` 回调中标记需要重连，下次收到音频帧时自动创建新的 Recognition 连接
2. `fastapi_app.py` 的 `ws_realtime_asr` relay loop: send_audio 前检测 `needs_reconnect`，为 True 则先调 `restart_session()`；send_audio 异常时也先尝试重连再 break
3. 客户端完全无感知——WS 不断开，SSE 不推 `recording-disconnected`

### 教训
- 云端服务不能假设始终在线——idle timeout、网络波动、服务重启都是常规事件
- 服务端与外部服务的连接断开不应级联影响到客户端
- 连接管理要用"检测→标记→下次使用时恢复"模式，而不是"断了就报错"

## §18 WS/SSE 错误耦合 — 暂停录音误关 SSE 导致会议"假死" (2026-07-14)

### 现象
点击"停止录音"后按钮卡住 ~30 秒才恢复；更严重的是，暂停录音竟会关闭 SSE 长连接，导致后续文档生成、demo 更新无法推送到客户端，会议实质上"假死"。

### 根因
`run_realtime_loop` 中无论哪种退出（结束 or 暂停），都无条件执行 `tokio::time::sleep(30s)` 然后设 `sse_active=false`。而 JS 侧 `await invoke("stop_capture")` 被这 30 秒阻塞，按钮无法更新状态。

这是历史遗留的 WS/SSE 耦合——早期架构中录音结束 = 会议结束，SSE 也跟着关。但产品需求是"暂停录音 ≠ 会议结束"。

### 修复 (v0.22.8 client, commit d42c8a6→06e42a0, 2 files)
1. **JS**: 按钮状态（"停止录音"→"开始录音"）在 `await invoke()` 之前就完成切换，不再被 Rust 阻塞
2. **Rust**: 暂停录音时直接 `return Ok(())`，不设 `sse_active=false`，SSE 保持连接；仅 `close_meeting=true` 时才等 30s 收事后事件再关 SSE
3. **JS**: `meeting-complete` 处理器检查按钮状态——如果已为 `idle`（用户暂停录音后的状态），不覆盖按钮文字

### 教训
- 录音 (WS) 和事件推送 (SSE) 是两个独立通道，应该独立管理生命周期
- UI 状态更新不应被底层网络操作阻塞——先用乐观更新再异步执行
