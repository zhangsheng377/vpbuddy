# VPBuddy 需求与架构理解校准

日期：2026-06-24

本文档记录一次面向开发人员的需求校准，目的是把当前产品意图与仓库中已有文档、README、实现之间可能产生误解的地方说清楚。它不是替代现有总体架构，而是给后续开发、重构和文档修订提供统一口径。

## 核心定位

VPBuddy 是会议过程中的 AI 协同执行系统。它在会议进行中持续接收音频、理解上下文、结构化累积需求信息，并实时生成文档与 Demo，最终把这些内容传回客户端展示给 VP。

它不是“会议结束后生成初稿”的纪要工具。会议一开始后，系统就应该持续产出可见内容：结构化事实、文档草稿、风险判断、候选结论、Demo 页面都应在客户端对应窗口中实时更新。

## 已确认的需求口径

### 实时展示是核心体验

服务端生成的内容不是会后才出现，也不是 VP 手动触发后才开始生成。音频流进入服务端后，系统应持续执行：

```text
客户端采集会议音频
  → 音频上传服务端
  → 服务端转写与说话人识别
  → 服务端结构化提取 5 类事实
  → 服务端并行生成 6 类文档与 Demo
  → 文档文本和 Demo 实时回传客户端
  → 客户端对应窗口实时展示
```

“实时”在这里首先是产品体验要求：VP 在会议中能不断看到内容演化，而不是等到会议结束后看到一版汇总。工程实现可以有分片、批处理、节流和延迟，但交互模型必须是持续更新。

### 结构化累积保持 5 类事实

当前 5 类结构化事实的划分是清晰且应保留的：

| 类型 | 含义 | 典型内容 |
|---|---|---|
| `REQ` | 需求 | 客户明确提出的业务或系统需求 |
| `GOAL` | 目标 | 客户想达成的业务结果、管理目标、项目目标 |
| `FEAT` | 功能点 | 可落到系统功能、页面、接口、流程的能力 |
| `RISK` | 风险 | 技术、交付、合规、范围、成本、依赖风险 |
| `QUE` | 待确认问题 | 含糊、矛盾、缺失、需要 VP 或客户确认的信息 |

这 5 类事实是后续文档和 Demo 的输入源，也是客户端展示的核心信息层。开发时应避免把它退化成普通会议纪要。

### 6 类交付物实时生成

当前 6 类交付物的划分也应保留：

| 交付物 | 说明 |
|---|---|
| 需求文档 | 从 `REQ`、`GOAL`、`FEAT` 中整理需求、范围、优先级和客户原话 |
| 架构文档 | 从需求、约束、风险中生成模块划分、技术方案、关键决策 |
| 任务拆解 | 将需求与架构转成开发任务、依赖关系和交付顺序 |
| API 设计 | 生成接口、字段、数据流、集成边界 |
| 风险分析 | 识别技术、交付、合规、范围和资源风险 |
| Demo | 实时制作可展示、可交互的候选产品原型 |

这 6 类内容应作为并行持续生成的窗口，而不是一次性离线产物。Demo 尤其需要强调“实时制作和实时展示”，它和文本类文档一样是会议中的动态输出。

## 客户端与服务端边界

当前产品口径不是“所有能力都完全在用户本地机器运行”。更准确的架构应是：

```text
VP 本地客户端
  - 采集系统音频或会议音频
  - 管理会议入口和用户交互
  - 展示结构化事实、文档、Demo、风险、建议
  - 接收 VP 的 steer、修改、采纳、忽略、外发动作

服务端
  - 接收客户端上传的音频流
  - 执行 ASR、说话人识别、结构化提取
  - 调度 5 类事实累积与 6 类交付物生成
  - 生成文档文本和 Demo
  - 将结果实时推送或返回客户端展示
```

因此，后续文档和 README 不应再简单表述为“数据完全不出设备”或“完全本地运行”。可以强调用户本地安装客户端、会议内容不直接交给会议平台插件、服务端可私有化部署或受控部署，但不能把当前真实形态描述成纯本地单机。

## AI 主动行为边界

AI 可以主动生成和展示结论、建议、风险判断、候选方案和候选决策，只要这些内容只展示给 VP。主动提出“这个需求优先级可能较高”“这里存在交付风险”“建议采用某种架构方向”是合理的，因为它仍然只是 VPBuddy 客户端内的候选信息，最终是否采纳由 VP 决定。

真正需要禁止的是对外动作：

| 行为 | 是否允许 | 说明 |
|---|---|---|
| 主动生成结论 | 允许 | 展示给 VP，帮助 VP 判断 |
| 主动提出建议 | 允许 | 作为候选建议，不代表最终决策 |
| 主动标注风险 | 允许 | 风险提醒是核心价值之一 |
| 主动推荐需求优先级 | 允许 | 作为候选判断，由 VP 确认或修改 |
| 主动更新文档窗口 | 允许 | 服务端实时生成，客户端实时展示 |
| 主动更新 Demo 窗口 | 允许 | Demo 应实时制作、实时展示 |
| 主动外发给客户 | 不允许 | 对外发送必须由 VP 明确触发 |
| 主动触发投屏 | 不允许 | 投屏属于会议软件，VPBuddy 不控制 |

边界应从“AI 不主动推结果”修正为“AI 可以主动给 VP 展示候选结果，但不能主动执行对外动作”。

## 关于投屏

投屏不是 VPBuddy 的产品职责。VPBuddy 负责生成和展示内容；如果 VP 想让客户看到内容，应该由 VP 在腾讯会议、飞书、Zoom、钉钉等会议软件里使用原生共享屏幕能力。

因此开发时不应把“投屏状态”“投屏中”“撤回投屏”“自动投屏”设计成 VPBuddy 的核心状态或流程。VPBuddy 只需要保证客户端窗口中内容实时、清晰、可控，至于是否共享给客户，由 VP 和会议软件处理。

## 与现有仓库表述的差别

### README 的“本地优先”需要重新措辞

当前 README 中强调“完全运行在 VP 自己机器，数据不上传云端”。这个说法与当前确认的客户端-服务端口径不一致。建议改成：

```text
VPBuddy 客户端安装在 VP 本地，用于采集音频和展示实时生成结果；音频流上传到受控服务端处理，服务端完成转写、结构化提取、文档生成和 Demo 生成，再将结果实时回传客户端。部署形态可支持私有化或团队自托管。
```

### 架构文档中的“本地单机闭环”需要弱化

总体架构文档里关于本地 loopback、ASR、本地知识库的设计仍有价值，但需要区分“客户端侧采集”和“服务端侧处理”。尤其是 ASR、说话人识别、LLM 文档生成、Demo 生成这类重计算能力，应按服务端能力设计。

### “会议结束即有初稿”不是正确心智

正确心智是“会议中持续有内容”。如果文档、UI 文案或 README 中出现“会后生成”“会议结束得到初稿”这类表达，应改为“会议中实时更新，会议结束时已有完整演化结果”。

### “AI 不主动推结果”需要改成“AI 不主动对外”

产品边界不是禁止 AI 主动给 VP 建议，而是禁止 AI 越过 VP 执行对外动作。后续实现疑问窗口、预准备内容、风险分析、Demo 建议时，都可以主动展示在客户端，但外发、分享、提交、投屏必须由 VP 操作。

## 开发重点

### 客户端展示模型

客户端应按窗口或区域持续展示服务端结果。至少需要承载：

- 实时转写或摘要流
- 5 类结构化事实
- 6 类交付物
- Demo 展示区
- AI 主动建议、风险提醒、待确认问题
- VP steer 输入与修改反馈

这些窗口不是静态报告查看器，而是会议中的动态工作台。服务端每次生成增量结果后，客户端应能更新对应窗口。

### 服务端生成模型

服务端应围绕“音频流 → 结构化事实 → 交付物生成 → 客户端展示”组织能力。即使内部为了效率采用轮询、批处理、缓存或并发 worker，对外表现也应是持续生成。

6 类交付物不应互相阻塞。某个文档或 Demo 生成失败时，其他窗口仍应继续更新，并把失败状态以开发人员可诊断、VP 可理解的方式展示。

### Demo 生成模型

Demo 是核心交付物，不是文档附件。它应该随着会议内容持续变化，并在客户端实时展示。实现上可以先生成 HTML 原型或轻量交互页面，再逐步增强为更复杂的组件化 Demo，但产品语义必须是“会议中实时制作”。

### 数据与同步

需要明确每个服务端输出的同步粒度：

| 输出 | 推荐同步粒度 |
|---|---|
| 转写文本 | 按音频段或稳定句段 |
| 结构化事实 | 按新增、修改、合并、确认状态变化 |
| 文档文本 | 按章节、版本或增量 diff |
| Demo | 按可渲染版本或资源包 |
| 风险与建议 | 按单条卡片 |
| 待确认问题 | 按问题卡片 |

同步协议可以后续再定，但产品层必须先承认它们是客户端实时展示对象。

## 一句话准则

VPBuddy 的核心体验是：VP 本地客户端采集会议音频并展示结果，服务端实时理解会议、生成结构化事实、文档和 Demo，再把候选结论、建议、风险和可交互 Demo 持续回传给 VP；VPBuddy 不主动外发，也不控制投屏。
