## 一、定位与设计目标

### 1.1 三句话定位

> **会议 = 人机协同过程**  
> **VPBuddy = 会议中的 AI 协同执行系统**  
> **本架构 = 把"后台并行累积+并行生成"这个抽象落到可运行的工程上**

**核心定位**(v1.3 修正):

> VPBuddy 是**后台会议操作系统**——会议开始时启动,后台**并行做两件事**:
> 1. **累积结构化信息**(客户需求 / 业务目标 / 风险点等)
> 2. **持续生成候选交付物**(Demo / 页面 / 数据模型 / 任务清单 / 工期等)
>
> VP 在会议中**主导一切**,任何时候调取,**已经有可投屏的交付物候选**;  
> VP 主动触发是对"已就绪成果"的**干预/调整/外发**;  
> AI 不主动推送、不抢话语权。  
>
> 整个系统**无实时性硬约束**: 后台并行任务无延迟目标,VP 主动干预后等 1-3min(人类耐受度)可接受。

### 1.2 设计目标 (按优先级)

| 优先级 | 目标 | 说明 |
| --- | --- | --- |
| P0 | **后台结构化累积** | 会议开始到结束,后台持续累积"客户需求/业务目标/风险点"等结构化数据 |
| P0 | **后台交付物并行生成** | 后台持续从结构化累积中生成候选交付物(Demo/页面/数据模型/任务清单等),VP 任何时候调取都已就绪 |
| P0 | **持续演化** | 交付物不是一次性生成,而是随对话增量更新、回滚、合并(版本树) |
| P0 | **知识库(展示+检索双模式)** | 个人/企业/行业三类知识;**展示模式**(`mode: constraint`)= 后台实时提取/展示,VP 可改但**不阻塞 AI 继续做**;**检索模式**(`mode: retrieval`)= 按需 RAG 检索历史案例 |
| P0 | **人类主导** | VP 主导一切;AI 不主动推送、不主动外发、不抢话语权 |
| P1 | **VP 主动干预** | VP 触发的调整/重生成/外发/撤回,1-3min 内完成(人类等待耐受度,软目标) |
| P1 | **多平台覆盖** | 腾讯会议 / 飞书 / 钉钉 / Zoom,接入层可插拔 |
| P1 | **Sub-agent 并行** | 产品/架构/UI/数据/风险五 Agent 并行推理,而非串行 |
| P2 | **可审计** | 会议时间轴可回放,可追溯"某项决策由谁触发/基于什么累积" |
| P2 | **可移植** | 不绑定单一 LLM/ASR/向量库,核心组件可替换 |

> **与 v1.2 的关键差异**: v1.2 把"持续累积"和"VP 主动触发"作为仅有的两条路径,弱化了"持续生成交付物";  
> v1.3 恢复"**后台交付物并行生成**"为 P0——VP 调取时,系统已经有可投屏的候选交付物,**不是空仓库**。  
> 这是 VPBuddy 跟飞书妙记/Notion AI 的根本差异:**不只是记录,还做出交付物**。

### 1.3 非目标(明确不做)

- **不是实时辅助工具**: VPBuddy 不试图"边听边给反馈",AI 不主动推送任何东西
- **不是纯会议录音/纪要工具**: VPBuddy 不只记录信息,核心是**做出交付物**;单纯记录(飞书妙记/通义听悟)不是它
- **不是通用 Agent 平台**: 不支持任意任务编排,所有能力对齐"会议 → 累积 + 生成 → 干预"主流程
- **不是代码 IDE**: Demo/页面/数据模型是"原型交付物",不直接进入生产代码库(生产由人类团队接手)

## 二、五大系统的关系(全景图)

```
                        ┌─────────────────────────────────────┐
                        │  人类决策层(VP / 售前 / 项目负责人)        │
                        │  - 主导控场 · 主动调取 · 显式确认        │
                        │  - 调取时已经有"可投屏的候选交付物"     │
                        └──────────────┬──────────────────────┘
                                       │ 主动调取/干预(异步,1-3min 等待可接受)
                                       ▼
   ┌─────────────────────────────────────────────────────────────┐
   │  ④ 指令控制层 Command Center                                │
   │  - 意图解析 · 路由到 ②/③/⑤                                  │
   │  - 状态机: 观察/草拟/待确认/已投屏                          │
   └──────────────┬──────────────────────────────┬───────────────┘
                  │                              │
   ┌──────────────▼──────────────┐   ┌───────────▼─────────────┐
   │  ② 会议理解 + Agent 系统     │◄──┤  ③ 交付物生成引擎         │
   │  Runtime Layer              │   │  Artifact Engine         │
   │  - 持续结构化累积(后台)      │   │  - 后台持续生成候选交付物  │
   │  - 5 Agent 并行推理         │   │  - 持续演化(版本树)        │
   └──────────────┬──────────────┘   └───────────┬─────────────┘
                  │                              ▲
                  │ 约束注入                      │ 监听 ② 累积
                  ▼                              │
   ┌──────────────────────────────────────────────┴──────────────┐
   │  ⑤ 统一知识库系统(约束而非检索)                               │
   │  个人(VP 经验) · 企业(PRD/规范/历史) · 行业(标准/竞品)         │
   └─────────────────────────────────────────────────────────────┘
                  ▲
                  │ 会议链接 / 平台 / 项目 / 知识库选择
   ┌──────────────┴──────────────────────────────────────────────┐
   │  ① 会议接入层 Join Meeting                                  │
   │  - 平台适配器(腾讯/飞书/钉钉/Zoom)                            │
   │  - 后台持续采集音/视/文                                       │
   └─────────────────────────────────────────────────────────────┘
```

**关键关系(与 v1.2 不同)**:
- ③ 交付物生成**不只是反向依赖 ②**,而是**与 ② 并行运行**: ② 累积同时,③ 持续从累积中生成候选交付物
- VP 调取时,③ 已经有可投屏的候选,不需要 VP 触发才开始

### 2.1 五个系统的职责一句话

| # | 系统 | 职责 |
| --- | --- | --- |
| ① | 会议接入层 | 把人/平台/项目/知识库"接进来",**后台持续采集**音/视/文 |
| ② | 会议理解 + Agent | **持续累积**结构化信息;5 Agent 并行推理,后台常驻 |
| ③ | 交付物生成引擎 | **后台持续生成候选交付物**,持续演化;不是 VP 触发才生成 |
| ④ | 指令控制层 | 唯一与 VP 对话的人机接口;把"自然语言指令"翻译为对 ②/③/⑤ 的操作 |
| ⑤ | 统一知识库 | 三类知识;**展示模式**(`mode: constraint`)= 后台实时提取并展示在 Demo/页面/数据模型上,VP 可改但**不阻塞** AI 继续生成;**检索模式**(`mode: retrieval`)= 按需 RAG |

### 2.2 系统之间的约束

- **① 不依赖 ②/③/④/⑤**: 接入层只负责"把信号持续采进来",保持纯净。
- **④ 是唯一对外**: ②/③ 都不直接接收人类指令,所有交互走 ④。
- **⑤ 是横切关注点**: ②/③ 任何累积/生成动作都要经过 ⑤ 校验。
- **② ③ 并行运行**: ② 累积同时 ③ 持续生成;③ 监听 ② 的累积事件触发增量更新,不需要 VP 介入。
- **② 内部自治**: ② 内部的 5 Agent 之间不直接通信,通过共享"累积状态"协同。
- **无实时性约束**: 五大系统都按"能跑就行"的节奏工作,无延迟目标。

## 三、核心数据流(三轨并行)

### 3.1 三轨全景

```
[会议开始]
    │
    ├───── ① 会议接入层: 持续采集音/视/文 ─────────────────┐
    │                                                        │
    │  [后台轨 1: 结构化累积]                                 │ [后台轨 2: 交付物生成]
    │                                                        │
    │  ② 会议理解层                                           │
    │    - ASR 转写                                            │
    │    - 多模态融合                                          │
    │    - 结构化提取 ──→ 写入"会议结构化状态"  ──→  ③ 交付物生成引擎
    │                                                        │   - 监听累积事件
    │    ② 5 Agent 并行推理(后台)                              │   - 持续增量更新
    │    ② 合并器                                             │   - Demo/页面/数据模型/任务
    │                                                        │   - 记录 diff 到版本树
    │                                                        ▼
    │                                                  "候选交付物"
    │                                                  (VP 任何时候调取都就绪)
    │                                                        │
    │                                                        │
    │  [前台轨 3: VP 主动干预]                                │
    │                                                        │
    │  VP 在会议中,主动发起某动作 ──→  ④ 指令控制层           │
    │    - 调整某个交付物    ──→  ③ 局部重生成                │
    │    - 重新生成某交付物  ──→  ③ 全量重生成                │
    │    - 投屏/外发         ──→  ③ 状态机跳转                │
    │    - 调用知识库        ──→  ⑤ 检索/约束                 │
    │    - 控制 AI 行为      ──→  ② 调整 prompt / 状态机      │
    │                                                        │
    │    (VP 不等结果,继续跟客户聊;1-3min 后静默通知)          │
    │                                                        │
[会议结束]                                                   │
    │                                                        │
[累积结果 + 候选交付物全部保留,VP 任何时候调取都完整]        │
```

### 3.2 关键点(与 v1.2 不同)

| 维度 | v1.2(错) | v1.3(对) |
| --- | --- | --- |
| ③ 交付物生成时机 | 仅 VP 触发时生成 | **后台持续生成 + VP 触发可重生成** |
| VP 调取时有什么 | 累积的结构化笔记 | **累积笔记 + 已就绪的候选交付物** |
| ③ 与 ② 关系 | ③ 反向依赖 ②(③ 监听 ② 事件) | **② ③ 并行运行**;③ 同时也是后台流水线 |
| 4 大交付物价值 | 没强调 | **后台已有 Demo/页面/数据模型/任务清单** 候选 |

### 3.3 状态机(交付物生命周期)

```
     后台草拟 ──VP 确认──▶ 投屏 ──VP 外发──▶ 已交付
       │(持续生成)            │                 │
       │  VP 撤回              │  VP 撤回         │  (不可变)
       ▼                      ▼                 ▼
     撤回(保留版本)       撤回(保留版本)     归档
       │
       ▼
     重新草拟(可基于旧版本)
```

**关键**: "后台草拟" 是常态——③ 后台持续生成新版本,旧版本保留形成版本树。VP 确认/投屏是显式动作,外发后版本不可变。

## 四、模块详细设计

### 4.1 ① 会议接入层

**核心组件**

- **平台适配器** (`meeting-adapters/<platform>`): 抽象接口 `MeetingAdapter`,每个平台实现一份
  - `腾讯会议`: SDK + Webhook(混用)
  - `飞书会议`: 飞书开放平台 + 事件订阅
  - `钉钉会议`: 钉钉开放平台
  - **Zoom**: Zoom SDK + Webhook(参考飞书妙记)
- **信号归一化**: 所有平台的音/视/文/屏幕 → 统一的 `StreamFrame { ts, type, payload, source }`
- **工作台初始化**: 加载用户身份/项目/知识库选择,创建"会议 session"
- **后台常驻采集**: 会议开始后,**持续**采集所有参会者的音/视/文,会议结束才停

**关键决策点**

| 决策 | 推荐 | 理由 |
| --- | --- | --- |
| 会议音频获取方式 | **SDK 混音流**(而非用户本地麦克风) | 拿到所有参会者的干净音轨,避免回声 |
| 屏幕共享捕获 | 平台原生截屏 API | 跨平台一致需要大量适配工作 |
| 采集频率 | 音频流式(实时),屏幕帧 1-2s/帧(够用即可) | 不卡延迟,够还原会议内容 |
| 缓冲策略 | 内存缓冲 + 定期落盘 | 断电/崩溃时不丢累积成果 |
| 断线重连 | 平台事件驱动,断线后自动重连 | 会议中网络抖动常见 |

### 4.2 ② 会议理解 + Agent 系统

**两层结构**

```
[信号流] → 会议理解层 → [累积状态] → Agent 推理层 → [更新建议]
              ↑                            ↓
              └── 状态机(单一可信源)←───────┘
```

**会议理解层 (单 Agent,持续运行)**

- **ASR 模块**: 流式语音转写(中文优先,英文支持)
- **多模态融合**: ASR + 屏幕 OCR + 文档解析 → 统一文本流
- **结构化提取**: 从文本流中持续提取"客户需求/业务目标/功能点/风险点/待确认",用 LLM 做带 schema 的 JSON 抽取
- **状态机**: 维护"当前会议结构化状态"作为单一可信源(Single Source of Truth)

**Agent 推理层 (5 Agent 持续并行)**

| Agent | 关注 | 输出 |
| --- | --- | --- |
| 产品 Agent | 业务目标、用户故事、PRD 风格 | 用户故事 / 业务流程图 / 原型建议 |
| 架构 Agent | 技术选型、模块划分、接口 | 架构图 / 技术栈 / 关键风险 |
| UI Agent | 页面布局、交互流程、视觉 | 页面 wireframe / 组件树 / 交互稿 |
| 数据 Agent | 数据模型、字段、关系、API | ER 图 / API 契约 / 数据流 |
| 风险 Agent | 性能/安全/合规/工期 | 风险清单 / 缓解方案 / 工期估算 |

**Agent 协同机制**

- **不直接通信**: 每个 Agent 独立读"会议状态",独立写"自己的更新建议"
- **冲突解决**: 合并器(主 Agent 或独立服务)按优先级合并:数据 > 架构 > UI > 产品 > 风险
- **共享约束**: 5 Agent 都从 ⑤ 知识库读取约束,但各自有独立的"约束视图"

**关键决策点**

| 决策 | 推荐 | 理由 |
| --- | --- | --- |
| Agent 编排框架 | **LangGraph** 或自研轻量状态机 | LangGraph 适合有状态+多分支,自研适合极致可控 |
| Agent 通信 | **共享状态 + 合并器** | 比"Agent 间点对点"更可观测、可调试 |
| Agent 数量 | 固定 5 个,**不动态增减** | 5 个是产品说明书定义,动态增删会破坏心智模型 |
| Agent LLM 选型 | **可异构**: 产品/UI 用大模型,数据/风险可用小模型 | 没有延迟约束,可按"质量"而非"速度"选 |

### 4.3 ③ 交付物生成引擎 (后台持续运行)

**v1.3 关键升级**: ③ 不是"VP 触发才生成",而是**后台持续生成**——VP 调取时已经有候选。

**交付物类型**

| 类型 | 形态 | 关键技术 |
| --- | --- | --- |
| **交互 Demo** (核心) | 可点击的 HTML/React 原型 | LLM + 模板 + 组件库 |
| 页面结构 | 页面 wireframe + 组件树 | UI Agent 输出,直接渲染 |
| 功能流程 | 流程图 / 时序图 | Mermaid / PlantUML 渲染 |
| 数据模型 | ER 图 + 字段表 | 数据 Agent 输出 |
| API 设计 | OpenAPI / GraphQL schema | 数据 Agent 输出 |
| 权限模型 | RBAC/ABAC 矩阵 | 风险 Agent + 数据 Agent |
| 开发任务 | 任务卡片列表(含工期) | 风险 Agent + 产品 Agent |
| 工期与里程碑 | 甘特图 / 里程碑表 | 风险 Agent |

**后台持续生成机制**

- **监听 ② 累积事件**: ② 累积状态变化时,③ 触发对应交付物的增量更新
- **每个交付物独立运行**: Demo/页面/数据模型/任务等可并行生成
- **每个交付物持续演化**: 增量更新产生新 commit,旧 commit 保留形成版本树
- **可中断**: VP 撤回时,正在生成的新版本自动作废
- **可降级**: 某个交付物生成失败不影响其他交付物

**VP 主动触发的特殊处理**

- VP 的"重生成某交付物"指令 → ③ 全量重生成该交付物(基于当前累积状态)
- VP 的"调整某交付物"指令 → ③ 局部重生成(基于现有版本 + 调整指令)
- VP 的"投屏/外发" → ③ 状态机跳转,投屏状态变更为"已就绪"

**关键技术选型**

| 决策 | 推荐 | 理由 |
| --- | --- | --- |
| 文档/数据模型存储 | **JSON + 版本树** | 比 SQLite/Mongo 更轻,适合频繁 diff |
| 交互 Demo 生成 | **沙箱 HTML + React** | VP 在浏览器内可点击,与生产解耦 |
| 渲染管线 | **LLM → 结构化 JSON → 模板渲染** | 避免 LLM 直接生成代码导致不可控 |
| 组件库 | **shadcn/ui 或 Ant Design** | 主流、好维护,符合企业级审美 |

### 4.4 ④ 指令控制层 (Command Center)

**唯一对外接口**,所有 VP 与 VPBuddy 的交互都走这里。

**子模块**

- **意图分类器**: 把自然语言指令路由到 ②/③/⑤
  - 关键词 + LLM few-shot
  - 支持 5 类(产品说明书 §七): 修改 UI/功能、生成 Demo、拆解任务、调用知识库、控制 AI 行为
- **状态机**: 每个交付物/会议/Agent 都有状态机
  - 状态: `观察 / 后台草拟 / 待确认 / 投屏 / 已交付 / 撤回`
  - 转换: 显式指令触发,不允许隐式跳转
- **多模态反馈**: 不仅文字,还支持: 屏幕高亮、语音播报、卡片/按钮
- **权限/审计**: 所有指令记录到会议时间轴,可回放

**关键决策点**

| 决策 | 推荐 | 理由 |
| --- | --- | --- |
| 反馈形式 | **卡片+按钮 > 纯文本** | 会议中没空打字,点击更自然 |
| 异步通知 | 任务完成后**静默通知**,不打断 VP 当前对话 | 符合"VP 主导"原则 |
| 指令历史 | **可回放 + 可编辑** | VP 经常需要"重复 3 分钟前的指令" |
| 多人协作 | **单 VP 主导,其他成员只读** | 避免多 VP 互相覆盖 |

### 4.5 ⑤ 统一知识库系统

**三类知识**

| 类型 | 内容 | 来源 | 更新频率 |
| --- | --- | --- | --- |
| **个人** | VP 经验、决策逻辑、方案习惯 | VP 显式输入 / 行为学习 | 低(随 VP 成长) |
| **企业** | PRD/MRD、技术规范、UI 规范、历史项目、SOP | 文档上传 / 知识库对接 | 中(项目演进) |
| **行业** | 行业标准方案、通用架构、竞品方案、最佳实践 | 定期抓取 / 人工编辑 | 高(行业变化) |

**关键定位(v1.5 彻底重写):后台实时展示,VP 可改但不阻塞**

> **v1.5 关键澄清**(用户原话):"应该是提取出约束/背景知识等一切东西,展示,允许 VP 修改但**不强制要求确认**,即**不会停下等待**,后台依然在按照当前约束继续做 demo。另外,约束也**不需要注入 system prompt**。"

**核心原则**(三个明确):
1. **不注入 system prompt**:约束/背景知识是给 VP 看的,不是塞进 LLM 的隐藏 prompt 让它"必须遵守"
2. **实时展示**:Agent 推理时,自动把识别的 constraint 在 Demo/页面/数据模型上**实时标注**
3. **不阻塞 AI**:VP 可以看、可以改、可以问、可以批复——但 AI **不等待 VP 反馈**,继续按当前约束做 demo

每条知识带 `mode` 字段,标识用途:

| mode | 展示位置 | 典型内容 | VP 行为 | AI 行为 |
| --- | --- | --- | --- | --- |
| `constraint` | Demo/页面/数据模型上**实时标注来源** | 规则/SOP/规范/UI 规范/技术栈限制/编码标准 | **可看、可改、可问、可批复**,不强制确认 | **不等待**,继续按当前约束生成 |
| `retrieval` | 侧栏弹窗列出 Top-k 检索结果,带来源链接 | 历史项目/案例/客户文档/外部资料 | 点"采纳"→ 替换当前 constraint;或忽略 | 检索失败不阻塞主流程 |

**展示模式工作流**(`mode: constraint`):
- Agent 推理时识别"这个设计用到了约束 X"
- 在 Demo 元素上挂载一个**可点击的来源标签**(右上角小角标)
- VP 点开看详情:"这个按钮用 #1890ff 因为企业 UI 规范 §3.2 规定"
- VP 改改 → 改动立即反映到 demo 元素;但 **AI 此时不一定重新生成**(版本树记录)
- VP 主动调取时才触发全量重生成

**检索模式工作流**(`mode: retrieval`):
- VP 问"参考下历史项目 X"或 Agent 遇到全新场景
- 侧栏弹出 Top-k 检索结果(标题+摘要+置信度+来源)
- VP 点"采纳"→ 检索内容**替换**当前 constraint,后续 AI 生成按新约束走
- VP 不采纳 → AI 继续用现有约束,不阻塞

**两类内容的边界**:
- 一份规范文档**通常同时含两种模式**:
  - 规则部分(`mode: constraint`)→ 在 demo 上展示
  - 案例部分(`mode: retrieval`)→ VP 按需检索
- 元数据示例:
  ```
  knowledge:
    title: "本企业 UI 规范 v2.1"
    sections:
      - title: "主色 #1890ff、辅色 #52c41a"
        mode: constraint        # 展示在 demo 元素上
        priority: high
        scope: [ui_agent, frontend_agent]
      - title: "按钮圆角案例 5 个"
        mode: retrieval         # VP 按需检索
        scope: [ui_agent]
  ```

**知识图谱结构**

```
个人 ─┐
     ├─→ 约束集 ─→ Agent 累积/生成 ─→ 交付物
企业 ─┤
行业 ─┘
```

每条知识带元数据:
- `scope`: 适用 Agent(产品/架构/UI/数据/风险/all)
- `priority`: 优先级(强制/建议/可选)
- `version`: 版本号(随时间更新)
- `confidence`: 置信度(影响是否覆盖 Agent 自身判断)

**关键决策点**

| 决策 | 推荐 | 理由 |
| --- | --- | --- |
| 知识存储 | **向量库 + 关系库双写** | 向量用于相似度,关系用于"继承/冲突" |
| 向量库选型 | **pgvector / Milvus / Qdrant** | 视部署规模,小团队 pgvector 够用 |
| 知识更新 | **PR 模式**(知识也是代码) | 重要知识需要审核,避免污染 |
| 行业知识抓取 | **人工编辑 + 定期审核** | 自动抓取质量不可控 |

## 五、关键机制(架构级)

### 5.1 后台并行运行机制

**v1.3 升级**: 不再是"持续累积+主动响应"双轨,而是"**后台并行三轨**"。

#### 5.1.1 后台结构化累积(无延迟目标)

- **持续运行**: 会议开始启动,会议结束停止;不卡延迟,能跑就行
- **增量累积**: 每次新输入增量更新结构化状态,不去重历史
- **定期落盘**: 内存累积 + 定期写入持久化存储,断电/崩溃时不丢
- **资源节制**: 闲时降频(1-2s 一次处理),忙时升频;不抢占 VP 设备的 CPU/内存
- **后台观察**: 关键指标(累积条目数、提取覆盖率、模型费用)实时记录,可查

#### 5.1.2 后台交付物并行生成(无延迟目标)

- **监听 ② 累积事件**: 累积状态变化时自动触发对应交付物的增量更新
- **每个交付物独立运行**: Demo/页面/数据模型/任务等可并行生成,互不阻塞
- **增量生成**: 基于现有版本 + 累积 diff,而不是全量重生成
- **版本树**: 每次更新产生新 commit,旧 commit 保留
- **可降级**: 某交付物生成失败不影响其他交付物
- **资源节制**: 与 ② 累积协调 CPU/内存使用,避免抢占

#### 5.1.3 VP 主动干预(1-3min 软目标)

- **任务队列**: VP 触发的动作进入任务队列,worker 池消费
- **异步完成**: 完成后**静默通知**,不打断 VP 当前对话
- **可中断**: VP 发起新指令时,正在执行的低优先级任务可作废
- **可降级**: LLM 故障时,显示"上一稳定版"+"任务执行中"
- **可重试**: 失败的任务可手动重试,不丢失累积状态

#### 5.1.4 通用保障

- **背压控制**: 累积过快时,合并多次输入再处理,避免雪崩
- **可解释性**: 任何"任务执行中"必须告诉 VP 当前在做什么(等 ASR? 等 LLM? 等渲染?)
- **错误恢复**: 任何单点故障不丢失累积状态;有重连/重试机制

### 5.2 Sub-agent 并行推理

- **任务队列**: 5 Agent 共享一个"累积状态变化"事件流
- **独立沙箱**: 每个 Agent 自己的 LLM 上下文,不互相污染
- **合并策略**: 见 4.2 冲突解决
- **观察性**: 每个 Agent 的输入/输出/耗时/费用都记录

### 5.3 交付物持续演化

- **不是"覆盖"**: 每次更新产生新 commit,旧 commit 保留
- **可回溯**: VP 随时"回到 5 分钟前的版本"
- **可对比**: 两个版本 diff 可视化
- **可合并**: 多个并行草拟可手动合并
- **可并行生成**: 多个交付物可同时增量更新,互不阻塞

#### 5.4.1 展示模式 (`mode: constraint`)

> **v1.5 澄清**: constraint 模式 = **后台实时提取并展示**,**不注入 system prompt**,**不阻塞 AI 继续做 demo**。

- **提取**: Agent 推理时**后台自动识别** applicable constraint(规则/SOP/规范/历史习惯)
- **展示**: 在 Demo/页面/数据模型上**实时标注**来源(右上角小角标/UI 标签/数据模型注释)
- **VP 交互**: 可以**看、改、问、批复**,**不强制确认**
- **不阻塞**: AI **不等待 VP 反馈**,继续按当前 constraint 生成 demo
- **优先级**: 由 knowledge.priority 字段控制(mandatory / recommended / optional)
- **版本**: constraint 更新时**不静默覆盖**,保留历史(版本树)
- **可解释**: 每个设计元素都带"来源"标签,VP 可追溯/why/why not
- **不注入 system prompt**:constraint 只展示给 VP 看,**不**塞进 LLM 的隐藏指令让 LLM "必须遵守"——LLM 按自己的理解生成,VP 通过 demo 的展示来"管理"约束

#### 5.4.2 检索模式 (`mode: retrieval`)

- **触发**: 
  - VP 显式问"我们做过类似项目吗"、"参考下历史项目 X"
  - Agent 遇到全新场景(没有 constraint 可循)
- **检索路径**: 向量相似度 + 元数据过滤(scope / project / tag)
- **展示**: 侧栏弹窗列出 Top-k 检索结果,带来源链接
- **采纳**: VP 点击"采纳"后,检索内容**替换当前 constraint**
- **防淹没机制**:
  - top-k 限制(默认 5)
  - 单条长度限制(默认 500 token)
  - relevance 阈值(默认 ≥ 0.7)
  - 总长度限制(retrieval 部分 ≤ 30% context window)
### 5.5 会议时间轴(需求演化)

**不是日志**,是"需求如何被构建为系统"的过程。

- 每个时间点: `t 时刻, 客户说 X → 累积到 Y → 触发 ③ 生成 Z`
- 可视化: 时间线 + 树形分支(回滚/并行)
- 检索: 按"功能/风险/决策"分类浏览
- 用途: 复盘 / 客户确认 / 团队交接

## 六、技术选型候选(请决策)

> v1.3 调整: 因为无延迟约束,选型可更宽松,以"质量/成本"为主要依据。
> 但因为**后台并行任务**多(累积 + 生成 + 5 Agent + 多交付物),需要考虑 worker 池规模和资源调度。

| 类别 | 推荐 | 备选 | 推荐理由 |
| --- | --- | --- | --- |
| **后端语言** | Python | Go / Node | LLM/ASR/数据科学生态最成熟 |
| **LLM 推理** | 主力 Claude / GPT-4 | 国产旗舰 | 质量优先,无延迟压力 |
| **Agent 编排** | LangGraph | 自研状态机 | 成熟 + 可视化 |
| **ASR** | 阿里通义/火山(中文),Whisper(英文) | 讯飞 | 成本 + 准确率平衡 |
| **向量库** | pgvector(小)/ Qdrant(大) | Milvus | 部署简单,够用 |
| **关系库** | PostgreSQL | MySQL | JSON + 全文检索 + 向量一站式 |
| **前端** | Next.js + React | Vue | 与 shadcn/ui 生态最佳 |
| **交互 Demo 沙箱** | iframe + React 渲染 | Monaco Editor | 隔离 + 真实可点 |
| **消息队列** | Redis Streams(轻量) | Kafka / RabbitMQ | 任务队列够用 |
| **存储** | NFS / S3 兼容对象存储 | - | 累积内容 + 交付物历史多,对象存储更合适 |
| **部署** | Docker + 单一主控 + 多 worker | Kubernetes | 初期不必上 K8s |
| **可观测** | OpenTelemetry + Langfuse | 自建 | 调试 LLM 必备 |

> ⚠️ **这些是建议,非强制**。实际选型请基于: 团队熟悉度、客户合规要求、预算。
> 决策后请写入 `docs/decisions/0001-xxx.md` 作为 ADR。

## 七、关键风险与开放问题

### 7.1 风险清单

| 风险 | 等级 | 缓解 |
| --- | --- | --- |
| LLM 幻觉导致 Demo 不可用 | 高 | 模板渲染约束 + 投屏前 VP 必须确认 + 知识库约束 |
| **后台交付物生成质量不达标** | **中** | 知识库约束 + 模板渲染 + 投屏前 VP 显式确认 |
| **演示模式被忽略**(VP 不看/修改,AI 继续按旧约束) | 中 | 在 Demo 上实时标注来源,VP 看到才会关注 |
| **检索结果选用不当** | 中 | 展示检索置信度+来源,VP 采纳后才替换 constraint |
| **后台运行异常**(崩溃/断电/断网) 导致累积/生成丢失 | 中 | 定期落盘 + 缓冲 + 重连 + 缺失标记 |
| **5 Agent 合并冲突**导致累积/生成错误 | 中 | 合并器优先级固定(数据>架构>UI>产品>风险) + 冲突日志 |
| 主动干预超时(>3min) | 低 | 任务队列监控;超时则通知 VP + 允许重发 |
| 多平台适配工作量大 | 中 | 抽象 `MeetingAdapter`,先做 1 个平台验证 |
| **约束类知识污染**(垃圾约束影响所有 Agent 推理) | 中 | PR 审核 + priority 字段 + 强制审批流 |
| **检索类知识陈旧/不准**(垃圾检索误导 LLM 引用) | 中 | relevance 阈值 + 时间衰减 + 来源标注 |
| 交付物版本树爆炸 | 中 | 自动归档(超过 100 版本折叠) |
| 客户隐私(会议内容含敏感信息) | 高 | 端到端加密 + 不存原始音频 + 数据隔离 |
| 成本失控(LLM 调用费) | 中 | 异构模型(大/小模型混用) + 缓存 + 预算告警 |
| VP 信任建立(担心 AI 抢活) | 中 | "人类主导" 原则 + AI 不主动推送 |

> **v1.3 风险表变化**: 新增"后台交付物生成质量不达标"(从 v1.2 的"累积遗漏"中分离出来)。

### 7.2 开放问题(请用户决策)

1. **第一平台**: 优先支持哪个会议平台?(建议:飞书,因为有现成妙记可参考)
2. **MVP 范围**: 5 大系统一次做完,还是先做"接入 + 累积 + 后台生成 + 按需取用"四件套?
3. **单租户 vs 多租户**: MVP 阶段是单租户(只服务一个公司)还是多租户?
4. **开源 vs 闭源**: 这套系统的核心模块是否开源?(影响选型)
5. **数据归属**: 会议累积内容 + 交付物存哪里?(本地 vs 云,影响合规)
