## 〇、口径校准 (v1.20, 2026-06-24)

本架构只服务于一个场景: **我(VP/创业者/产品经理)日常跟各种人开会时，需要能把讨论内容实时沉淀为 6 类结构化物(需求/架构/任务/API/风险/Demo HTML)。沉淀物可以跟同龄人协作讨论，也可以作为下一个会议的上下文。**

### 不是:
- ❌ 不是通用 AI agent 框架
- ❌ 不是会议录播/回放/编解码系统
- ❌ 不是客服聊天机器人
- ❌ 不是企业内部知识管理系统 (但聊天上传可充当)
- ❌ **不是展示项目 / POC / demo** — 是真生产工具

### 用户故事一句话:
> "我开会时开着 VPBuddy 客户端自动收声，会议开始 15 秒后就有 6 类文档 + 1 个 HTML 原型 Demo，我还能跟 AI agent 对话追问细节、调整方向。"

### v1.45 关键变更 (2026-07-12)

| 变更 | 旧 (v1.44) | 新 (v1.45) |
|------|-----------|-----------|
| SSE 重连恢复 | 全量重放历史事件 | **读取 Last-Event-ID** (header/query), 只推增量 |
| `doc-update` SSE | 推送完整 `content` 字段 | **只推元信息** `{kind, status, doc_size}`, 客户端按需 GET |
| Chat 文件上传 | 文本内容完整塞进 prompt | **只放文件路径**, agent 用 `read_file` 按需读取 |
| 图片上传 | 只转 base64 data URI, 不写盘 | **落盘 `uploads/{mid}/`** + 路径注入 prompt |
| KB 去重 | `content_hash` 全局查询 | **加 `user_id` 过滤**, 防止跨用户误判重复 |
| 文档触发去重 | hash 包含 `latest_demo_content` → 自反馈风险 | **只用 `cleaned_text` hash** |
| `_kick_docs` 阈值 | `len(cur) > 10` | **> 50**, 与 gkd 对齐 |

### v1.46 关键变更 (2026-07-12) — 本次

| 变更 | 旧 (v1.45) | 新 (v1.47) |
|------|-----------|-----------|
| Vision 路由 | `config.yaml` 只设 `provider`/`model`，fallback 到全局 MiniMax key → 401 | **三层逃生通道 (ADR-0054)**: monkeypatch Hermes 路由 + `OPENAI_*` 从 `DASHSCOPE_API_KEY` 兜底 + mmx-cli MiniMax 原生 VLM 后备 |

| .env 加载 | `bash run.sh` 手动 export (易丢失) | **多路径自动 fallback** + `OPENAI_*` 从 `DASHSCOPE_API_KEY` 兜底推导 |
| idle 文案 | 客户端显示 `"未连接"` (误解 → 以为服务断了) | **`"录音就绪"`** (录音断开 ≠ 服务断开) |

### v1.44 关键变更 (2026-07-12)

| 变更 | 旧 (v1.43) | 新 (v1.44) |
|------|-----------|-----------|
| SSE 生命周期 | 绑定 `capturing` flag, 停采集即断开 | **独立 `sse_active` flag**, 停采集后保持 30s 以接收事后事件 |

| 服务端启动 | `vpbuddy ui --port 8765` (无百炼 key) | **`bash run.sh`** (注入 BAILIAN_API_KEY + DASHSCOPE_API_KEY) |

## 二、ASR 架构 (v1.43 重写)

### 百炼 Fun-ASR-Realtime

```
客户端 PCM 帧 (16kHz mono int16)
  └─ WebSocket ─→ GPU 服务器 (fastapi_app.py)
                    └─ dashscope Recognition ─→ 百炼云端 WS
                                               │
                                               ▼
                                          sentence_end callback
                                               │
                    ┌──────────────────────────┘
                    ▼
              BailianCallback.on_event()
              ├─ 推送 transcript JSON 回客户端
              └─ 写入 MeetingState.cleaned_text (每句追加)
```

**关键设计**:
1. **单条 WS 连接**: 从 start 到 stop 同一条流，不 restart，模型内部自然利用上文语音特征
2. **句子级写入**: 每句 `sentence_end=True` 时立刻写 `cleaned_text`，文档 agent 实时可见
3. **无外部上下文注入**: dashscope Recognition API 不接受外部 context 参数，也不需要——WS 双工流天然带上下文

## 三、文档自驱动轮询 (v1.43 新增, v1.44 更新)

### 架构

**gkd 守护线程** (global_kick_docs) 每 6 秒扫描所有会议, 替代旧有的每个 WS 连接独立 poll 自驱动:

```python
# fastapi_app.py — 模块级 gkd daemon thread
def _gkd_loop():
    while True:
        sleep(6)
        for mid in recent_meetings:
            state = storage.load(mid)
            cur = state.cleaned_text or ""
            if not cur.strip():     # v1.46: 空文本跳过
                continue
            if hash_changed:        # v1.46: 无字数阈值，hash 为准
                task_manager.submit(mid, _gkd_runner)  # 并行 batch_docs + demo
```

**时间线**:
```
T+0s   WebSocket ASR 连接建立
T+1s   开始说话 → 逐句转写 → 写入 cleaned_text
T+6s   gkd 扫描 → 非空 cur 且 hash 变化 → 提交文档生成任务
T+25s  5/6 文档就绪 (batch_docs)
T+45s  demo 通常就绪 (6/6, 仅有实质内容时才写入版本)
...
会议结束 → close → 最后一轮 + 经验蒸馏 + SSE 保持 30s (v1.44)
```

### SSE 生命周期 (v1.44 新增)

客户端使用 **双 flag** 解耦音频采集与事件流:

| flag | 控制范围 | 设 true | 设 false |
|------|---------|---------|----------|
| `capturing` | 音频采集 + WS 发送 | `start_realtime_capture` | 用户点"停止采集"或音频设备初始化失败 |
| `sse_active` | SSE 事件流 (独立) | `start_realtime_capture` (与 capturing 同时) | `run_realtime_loop` 在 `POST /close` 后 **等 30 秒** |

**关键设计原则**:
- 停采集 ≠ 停会议 — `stop_capture` 只设 `capturing=false`, 不碰 `sse_active`
- WS `send_frame()` 失败只 `break` 发送循环, 不设任何 flag
- SSE 在 close 后额外保持 30 秒, 确保接收 `demo-new-version`、`doc-update` 等异步生成的事件
- GPT 4-5-10 之前 `capturing` 一拖三 (cpal/WS/SSE) 导致 "WS 断连→杀 SSE→demo 送达失败"

## 五、文档类型

| 文档 | 生成方式 | 内容风格 |
|------|----------|----------|
| req.md | batch_docs (1 次 LLM 调用 5 文档) | 需求分析, bullet points |
| arch.md | batch_docs | 架构方案, 或占位 |
| tasks.md | batch_docs | 任务拆分 |
| api.md | batch_docs | 接口定义, 或占位 |
| risk.md | batch_docs | 风险评估, RISK-XXXXXX 唯一编号 |
| demo HTML | demo agent (独立) | HTML 原型, 可交互, 多版本 |

所有文档生成通过 **MiniMax-M3** LLM。

### demo 版本管理 (v1.44 更新)

**版本写入流程** (`demo_version.write_demo_version`):
1. 读取现有 manifest → 确定下一版本号 vN
2. 写入 `demo_vN.html` + 更新 `demo_manifest.json` + 更新 `demo_latest.html` symlink
3. **内容检查** (v1.44): HTML < 3KB 且含"等待更多会议内容"/"暂无会议内容" → **拒绝写入**, 返回 `skipped: "placeholder"`
4. 成功 → 推送 SSE `demo-new-version` (version/summary/file_size/file) + 触发 proactive agent

**文件结构**:
```
docs/{meeting_id}/
├── demo_v1.html          # 版本 1
├── demo_v2.html          # 版本 2
├── demo_vN.html          # 最新版
├── demo_latest.html      # symlink → 最新版
└── demo_manifest.json    # [{version, created_at, trigger, summary, file_size, file}, ...]
```

## 六、数据流 (完整)

```
语音输入 (客户端麦克风)
  → PCM 帧 (16kHz mono int16)
  → WebSocket → 百炼 Fun-ASR-Realtime (云端, 实时逐句)
  → BailianCallback
     ├─ transcript JSON → WS 回客户端 (实时文字)
     └─ MeetingState.cleaned_text += 新句子 (每句追加)
  → 15s 后 → 自驱动 poll 提交 task_manager
     → batch_docs agent (fork 自 chat)
        → AIAgent.chat(prompt) → MiniMax-M3 → write_file × 5
     → demo agent (fork 自 chat)
        → AIAgent.chat(prompt) → MiniMax-M3 → write_file HTML
  → SSE doc-update / demo-new-version 事件
  → 客户端 6 文档面板更新
  → 每 30s → poll 检查增量 → 有增长就重新触发
  → close → 经验蒸馏 + 最终一轮文档
```
