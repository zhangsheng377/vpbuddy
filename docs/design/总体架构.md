## 一、定位与设计目标

### 1.1 三句话定位

> **会议 = 人机协同过程**  
> **VPBuddy = 会议中的 AI 协同执行系统**  
> **本架构 = 把这个抽象落到可运行的工程上**

### 1.2 设计目标 (按优先级)

| 优先级 | 目标 | 说明 |
| --- | --- | --- |
| P0 | **实时性** | 会议中"边说边出交付物",延迟控制在人可接受节奏(发言→响应 ≤ 8s) |
| P0 | **持续演化** | 交付物不是一次性生成,而是随对话增量更新、回滚、合并 |
| P0 | **知识库约束** | 个人/企业/行业三类知识,作为 AI 生成的隐式约束(而非检索结果) |
| P0 | **人类主导** | 所有关键动作(确认、投屏、外发)必须由 VP 显式触发,AI 不自动外发 |
| P1 | **多平台覆盖** | 腾讯会议 / 飞书 / 钉钉 / Zoom,接入层可插拔 |
| P1 | **Sub-agent 并行** | 产品/架构/UI/数据/风险五 Agent 并行推理,而非串行 |
| P2 | **可审计** | 会议时间轴完整记录"需求如何被构建为系统",可回放、可决策追溯 |
| P2 | **可移植** | 不绑定单一 LLM/ASR/向量库,核心组件可替换 |

### 1.3 非目标(明确不做)

- **不是会议录音/纪要工具**: 不替代飞书妙记、通义听悟;VPBuddy 关注"决策与交付",不关注"信息留存"。
- **不是通用 Agent 平台**: 不支持任意任务编排,所有能力对齐"会议 → 交付物"主流程。
- **不是代码 IDE**: Demo/页面/数据模型是"原型交付物",不直接进入生产代码库(生产由人类团队接手)。

## 二、五大系统的关系(全景图)

```
                        ┌─────────────────────────────────────┐
                        │  人类决策层(VP / 售前 / 项目负责人)        │
                        │  - 显式确认 · 投屏 · 外发 · 撤回       │
                        └──────────────┬──────────────────────┘
                                       │ 自然语言指令 / 确认
                                       ▼
   ┌─────────────────────────────────────────────────────────────┐
   │  ④ 指令控制层 Command Center                                │
   │  - 意图解析 · 路由到 ②/③/⑤                                  │
   │  - 状态机: 观察/草拟/待确认/已投屏                          │
   └──────────────┬──────────────────────────────┬───────────────┘
                  │                              │
   ┌──────────────▼──────────────┐   ┌───────────▼─────────────┐
   │  ② 会议理解 + Agent 系统     │   │  ③ 交付物生成引擎         │
   │  Runtime Layer              │   │  Artifact Engine         │
   │  - ASR/屏幕/文本融合         │◄──┤  - Demo · 页面 · 数据模型 │
   │  - 需求结构化                │   │  - API · 权限 · 任务      │
   │  - 5 Agent 并行推理         │   │  - 持续演化(版本树)        │
   └──────────────┬──────────────┘   └───────────┬─────────────┘
                  │                              ▲
                  │ 检索/约束注入                 │ 调用
                  ▼                              │
   ┌──────────────────────────────────────────────┴──────────────┐
   │  ⑤ 统一知识库系统(约束而非检索)                               │
   │  个人(VP 经验) · 企业(PRD/规范/历史) · 行业(标准/竞品)         │
   └─────────────────────────────────────────────────────────────┘
                  ▲
                  │ 会议链接 / 平台 / 项目 / 知识库选择
   ┌──────────────┴──────────────────────────────────────────────┐
   │  ① 会议接入层 Join Meeting                                  │
   │  - 平台适配器(腾讯/飞书/钉钉/Zoom)                            │
   │  - 初始化工作台 + 加载知识库 + 启动 Agent 运行时              │
   └─────────────────────────────────────────────────────────────┘
```

### 2.1 五个系统的职责一句话

| # | 系统 | 职责 |
| --- | --- | --- |
| ① | 会议接入层 | 把人/平台/项目/知识库"接进来",初始化运行时 |
| ② | 会议理解 + Agent | 把"客户在说什么"结构化为可执行的需求,5 Agent 并行推理 |
| ③ | 交付物生成引擎 | 把结构化需求转成"可投屏/可交付"的产物,持续演化 |
| ④ | 指令控制层 | 唯一与 VP 对话的人机接口,把"自然语言"翻译为对 ②/③/⑤ 的操作 |
| ⑤ | 统一知识库 | 三类知识的"约束源",影响 ② 的推理和 ③ 的生成,不是检索结果 |

### 2.2 系统之间的约束

- **① 不依赖 ②/③/④/⑤**: 接入层只负责"把信号送进来",保持纯净。
- **④ 是唯一对外**: ②/③ 都不直接接收人类指令,所有交互走 ④。
- **⑤ 是横切关注点**: ②/③ 任何生成动作都要经过 ⑤ 校验。
- **③ 反向依赖 ②**: ③ 监听 ② 的结构化输出,触发增量更新。
- **② 内部自治**: ② 内部的 5 Agent 之间不直接通信,通过共享"会议结构化状态"协同。

## 三、核心数据流(闭环)

### 3.1 主循环(单次发言)

```
[客户发言 / 屏幕 / 文档]
        │
        ▼ (毫秒级)
① 会议接入层: 信号归一化(平台无关的 stream frame)
        │
        ▼ (≤ 1s)
② 会议理解: ASR 转写 + 多模态融合 → 增量更新"会议结构化状态"
        │            ├ 客户需求 / 业务目标 / 功能点 / 风险点 / 待确认
        │
        ▼ (≤ 3s, 并行)
② Agent 系统: 5 Agent 读"会议状态"+"知识库约束" → 输出各自的更新建议
        │
        ▼ (≤ 1s, 合并)
② 合并器: 多 Agent 提议合并/冲突解决,产出"待生成指令"列表
        │
        ▼ (≤ 2s, 异步)
③ 交付物生成: 按指令增量更新对应交付物,记录 diff 到版本树
        │
        ▼ (实时)
④ 投屏/确认: 在 VP 主屏幕高亮"本轮新内容",等待显式确认
```

**单次发言的总延迟**: ≤ 8s(可接受节奏,人类不会感到卡顿)。

### 3.2 副循环(VP 主动指令)

```
[VP 指令] → ④ 意图解析
        │  ├ 修改 UI(→ ③ 局部重生成)
        │  ├ 生成 Demo(→ ③ 全新产物)
        │  ├ 拆解任务(→ ③ 输出开发任务列表)
        │  ├ 调用知识库(→ ⑤ 检索 + 注入约束)
        │  └ 控制 AI 行为(→ ② 调整 Agent prompt / 状态机)
        ▼
③ ⑤ 执行 + ② 同步状态
        │
        ▼
④ 反馈"已处理 / 已拒绝(原因)"
```

### 3.3 状态机(交付物生命周期)

```
     草拟 ──VP 确认──▶ 投屏 ──VP 外发──▶ 已交付
       │                 │                  │
       │  VP 撤回         │  VP 撤回          │  (不可变)
       ▼                 ▼                  ▼
     撤回(保留版本)   撤回(保留版本)     归档
       │
       ▼
     重新草拟(可基于旧版本)
```

**关键**: 任何"撤回"不删除历史,版本树保留完整演化过程(对应产品说明书的"会议时间轴")。

## 四、模块详细设计

### 4.1 ① 会议接入层

**核心组件**

- **平台适配器** (`meeting-adapters/<platform>`): 抽象接口 `MeetingAdapter`,每个平台实现一份
  - `腾讯会议`: SDK + Webhook(混用)
  - `飞书会议`: 飞书开放平台 + 事件订阅
  - `钉钉会议`: 钉钉开放平台
  - **Zoom**: Zoom SDK + Webhook(参考飞书妙记)
- **信号归一化**: 所有平台的音/视/文/屏幕 → 统一的 `StreamFrame { ts, type, payload, source }`
- **工作台初始化**: 加载用户身份/项目/知识库选择,创建"会议 session"

**关键决策点**

| 决策 | 推荐 | 理由 |
| --- | --- | --- |
| 会议音频获取方式 | **SDK 混音流**(而非用户本地麦克风) | 拿到所有参会者的干净音轨,避免回声 |
| 屏幕共享捕获 | 平台原生截屏 API | 跨平台一致需要大量适配工作 |
| 实时延迟目标 | 音频 ≤ 1s,屏幕帧 ≤ 2s | 与主循环 P0 实时性约束对齐 |

### 4.2 ② 会议理解 + Agent 系统

**两层结构**

```
[信号流] → 会议理解层 → [结构化状态] → Agent 推理层 → [更新建议]
              ↑                            ↓
              └── 状态机(单一可信源)←───────┘
```

**会议理解层 (单 Agent,串行)**

- **ASR 模块**: 流式语音转写(中文优先,英文支持)
- **多模态融合**: ASR + 屏幕 OCR + 文档解析 → 统一文本流
- **结构化提取**: 从文本流中增量提取"客户需求/业务目标/功能点/风险点/待确认",用 LLM 做带 schema 的 JSON 抽取
- **状态机**: 维护"当前会议结构化状态"作为唯一可信源(Single Source of Truth)

**Agent 推理层 (5 Agent 并行)**

| Agent | 关注 | 输出 |
| --- | --- | --- |
| 产品 Agent | 业务目标、用户故事、PRD 风格 | 用户故事 / 业务流程图 / 原型建议 |
| 架构 Agent | 技术选型、模块划分、接口 | 架构图 / 技术栈 / 关键风险 |
| UI Agent | 页面布局、交互流程、视觉 | 页面 wireframe / 组件树 / 交互稿 |
| 数据 Agent | 数据模型、字段、关系、API | ER 图 / API 契约 / 数据流 |
| 风险 Agent | 性能/安全/合规/工期 | 风险清单 / 缓解方案 / 工期估算 |

**Agent 协同机制**

- **不直接通信**: 每个 Agent 独立读"会议状态",独立写"自己的更新建议"
- **冲突解决**: 合并器(主 Agent 或独立服务)按优先级合并:数据 > 架构 > UI > 产品 > 风险
- **共享约束**: 5 Agent 都从 ⑤ 知识库读取约束,但各自有独立的"约束视图"

**关键决策点**

| 决策 | 推荐 | 理由 |
| --- | --- | --- |
| Agent 编排框架 | **LangGraph** 或自研轻量状态机 | LangGraph 适合有状态+多分支,自研适合极致可控 |
| Agent 通信 | **共享状态 + 合并器** | 比"Agent 间点对点"更可观测、可调试 |
| Agent 数量 | 固定 5 个,**不动态增减** | 5 个是产品说明书定义,动态增删会破坏心智模型 |
| Agent LLM 选型 | **异构**: 产品/UI 用大模型,数据/风险可用小模型 | 成本与质量平衡 |

### 4.3 ③ 交付物生成引擎

**交付物类型**

| 类型 | 形态 | 关键技术 |
| --- | --- | --- |
| **交互 Demo** (核心) | 可点击的 HTML/React 原型 | LLM + 模板 + 组件库 |
| 页面结构 | 页面 wireframe + 组件树 | UI Agent 输出,直接渲染 |
| 功能流程 | 流程图 / 时序图 | Mermaid / PlantUML 渲染 |
| 数据模型 | ER 图 + 字段表 | 数据 Agent 输出 |
| API 设计 | OpenAPI / GraphQL schema | 数据 Agent 输出 |
| 权限模型 | RBAC/ABAC 矩阵 | 风险 Agent + 数据 Agent |
| 开发任务 | 任务卡片列表(含工期) | 风险 Agent + 产品 Agent |
| 工期与里程碑 | 甘特图 / 里程碑表 | 风险 Agent |

**持续演化机制 (核心)**

- **版本树**: 每个交付物是 Git-like 的 DAG(节点 = 一次生成,边 = 增量关系)
- **增量更新**: 不是"重生成",而是"diff + apply"
- **VP 控制**: 撤回(回到任一历史版本)/ 合并(把多个分支合并)/ 锁定(冻结某版本)
- **投屏状态**: 投屏的是某个 commit,不是 working tree

**关键技术选型**

| 决策 | 推荐 | 理由 |
| --- | --- | --- |
| 文档/数据模型存储 | **JSON + 版本树** | 比 SQLite/Mongo 更轻,适合频繁 diff |
| 交互 Demo 生成 | **沙箱 HTML + React** | VP 在浏览器内可点击,与生产解耦 |
| 渲染管线 | **LLM → 结构化 JSON → 模板渲染** | 避免 LLM 直接生成代码导致不可控 |
| 组件库 | **shadcn/ui 或 Ant Design** | 主流、好维护,符合企业级审美 |

### 4.4 ④ 指令控制层 (Command Center)

**唯一对外接口**,所有 VP 与 VPBuddy 的交互都走这里。

**子模块**

- **意图分类器**: 把自然语言指令路由到 ②/③/⑤
  - 关键词 + LLM few-shot
  - 支持 5 类(产品说明书 §七): 修改 UI/功能、生成 Demo、拆解任务、调用知识库、控制 AI 行为
- **状态机**: 每个交付物/会议/Agent 都有状态机
  - 状态: `观察 / 草拟 / 待确认 / 投屏 / 已交付 / 撤回`
  - 转换: 显式指令触发,不允许隐式跳转
- **多模态反馈**: 不仅文字,还支持: 屏幕高亮、语音播报、卡片/按钮
- **权限/审计**: 所有指令记录到会议时间轴,可回放

**关键决策点**

| 决策 | 推荐 | 理由 |
| --- | --- | --- |
| 反馈形式 | **卡片+按钮 > 纯文本** | 会议中没空打字,点击更自然 |
| 指令历史 | **可回放 + 可编辑** | VP 经常需要"重复 3 分钟前的指令" |
| 多人协作 | **单 VP 主导,其他成员只读** | 避免多 VP 互相覆盖 |

### 4.5 ⑤ 统一知识库系统

**三类知识**

| 类型 | 内容 | 来源 | 更新频率 |
| --- | --- | --- | --- |
| **个人** | VP 经验、决策逻辑、方案习惯 | VP 显式输入 / 行为学习 | 低(随 VP 成长) |
| **企业** | PRD/MRD、技术规范、UI 规范、历史项目、SOP | 文档上传 / 知识库对接 | 中(项目演进) |
| **行业** | 行业标准方案、通用架构、竞品方案、最佳实践 | 定期抓取 / 人工编辑 | 高(行业变化) |

**关键定位:约束而非检索**

- ❌ **不是 RAG**: 不是"用户问 → 检索 → 拼接 prompt"
- ✅ **是约束注入**: 每个 Agent 推理时,系统从 ⑤ 取"相关约束",作为 system prompt 的隐式部分
- 优势: 约束的"权重"和"应用范围"可控制,不会出现"检索结果淹没 prompt"

**知识图谱结构**

```
个人 ─┐
     ├─→ 约束集 ─→ Agent 推理 ─→ 交付物
企业 ─┤
行业 ─┘
```

每条知识带元数据:
- `scope`: 适用 Agent(产品/架构/UI/数据/风险/all)
- `priority`: 优先级(强制/建议/可选)
- `version`: 版本号(随时间更新)
- `confidence`: 置信度(影响是否覆盖 Agent 自身判断)

**关键决策点**

| 决策 | 推荐 | 理由 |
| --- | --- | --- |
| 知识存储 | **向量库 + 关系库双写** | 向量用于相似度,关系用于"继承/冲突" |
| 向量库选型 | **pgvector / Milvus / Qdrant** | 视部署规模,小团队 pgvector 够用 |
| 知识更新 | **PR 模式**(知识也是代码) | 重要知识需要审核,避免污染 |
| 行业知识抓取 | **人工编辑 + 定期审核** | 自动抓取质量不可控 |

## 五、关键机制(架构级)

### 5.1 实时性保障

- **流式优先**: ASR 用流式接口,边说边出文本
- **并发执行**: 5 Agent 并行推理(非串行),LLM 调用并行
- **预测渲染**: 在"草拟"阶段就预渲染 Demo,VP 确认时几乎零延迟
- **降级策略**: 网络/LLM 故障时,显示"上一稳定版"+"加载中"
- **背压控制**: 客户连珠炮发言时,合并多次输入再触发 Agent,避免雪崩

### 5.2 Sub-agent 并行推理

- **任务队列**: 5 Agent 共享一个"会议状态变化"事件流
- **独立沙箱**: 每个 Agent 自己的 LLM 上下文,不互相污染
- **合并策略**: 见 4.2 冲突解决
- **观察性**: 每个 Agent 的输入/输出/耗时/费用都记录

### 5.3 交付物持续演化

- **不是"覆盖"**: 每次更新产生新 commit,旧 commit 保留
- **可回溯**: VP 随时"回到 5 分钟前的版本"
- **可对比**: 两个版本 diff 可视化
- **可合并**: 多个并行草拟可手动合并

### 5.4 知识库作为约束

- **作用域**: 每条知识声明适用于哪些 Agent
- **优先级**: 强制 > 建议 > 可选
- **冲突消解**: 新知识 vs 旧知识 → 显式版本号,不静默覆盖
- **可解释**: Agent 决策时,可以说"我依据 [知识 X] 做了 [选择 Y]"

### 5.5 会议时间轴(需求演化)

**不是日志**,是"需求如何被构建为系统"的过程。

- 每个时间点: `t 时刻, 客户说 X → 触发 Y → 产生 Z`
- 可视化: 时间线 + 树形分支(回滚/并行)
- 检索: 按"功能/风险/决策"分类浏览
- 用途: 复盘 / 客户确认 / 团队交接

## 六、技术选型候选(请决策)

| 类别 | 推荐 | 备选 | 推荐理由 |
| --- | --- | --- | --- |
| **后端语言** | Python | Go / Node | LLM/ASR/数据科学生态最成熟 |
| **LLM 推理** | 主力 Claude / GPT-4,小任务用国产模型 | 全用一家 | 异构降低锁定 |
| **Agent 编排** | LangGraph | 自研状态机 | 成熟 + 可视化 |
| **ASR** | 阿里通义/火山(中文),Whisper(英文) | 讯飞 | 成本 + 准确率平衡 |
| **向量库** | pgvector(小)/ Qdrant(大) | Milvus | 部署简单,够用 |
| **关系库** | PostgreSQL | MySQL | JSON + 全文检索 + 向量一站式 |
| **前端** | Next.js + React | Vue | 与 shadcn/ui 生态最佳 |
| **交互 Demo 沙箱** | iframe + React 渲染 | Monaco Editor | 隔离 + 真实可点 |
| **消息队列** | Redis Streams | Kafka | 轻量,会议级别吞吐够用 |
| **部署** | Docker + 单一主控 + 多 worker | Kubernetes | 初期不必上 K8s |
| **可观测** | OpenTelemetry + Langfuse | 自建 | 调试 LLM 必备 |
| **存储** | NFS / S3 兼容对象存储 | - | Demo 文件大,对象存储更合适 |

> ⚠️ **这些是建议,非强制**。实际选型请基于: 团队熟悉度、客户合规要求、预算。
> 决策后请写入 `docs/decisions/0001-xxx.md` 作为 ADR。

## 七、关键风险与开放问题

### 7.1 风险清单

| 风险 | 等级 | 缓解 |
| --- | --- | --- |
| LLM 幻觉导致 Demo 不可用 | 高 | 模板渲染约束 + 投屏前 VP 必须确认 |
| 实时性不足(发言→响应 > 8s) | 高 | 并行 Agent + 流式输出 + 预测渲染 |
| 多平台适配工作量大 | 中 | 抽象 `MeetingAdapter`,先做 1 个平台验证 |
| 知识库污染(垃圾知识影响生成) | 中 | PR 审核 + 优先级 + 冲突检测 |
| 交付物版本树爆炸 | 中 | 自动归档(超过 100 版本折叠) |
| 客户隐私(会议内容含敏感信息) | 高 | 端到端加密 + 不存原始音频 + 数据隔离 |
| 成本失控(LLM 调用费) | 中 | 异构模型 + 缓存 + 预算告警 |
| VP 信任建立(担心 AI 抢活) | 中 | "人类主导" 原则 + AI 不可自动外发 |

### 7.2 开放问题(请用户决策)

1. **第一平台**: 优先支持哪个会议平台?(建议:飞书,因为有现成妙记可参考)
2. **MVP 范围**: 5 大系统一次做完,还是先做"接入 + 理解 + Demo"核心三件套?
3. **单租户 vs 多租户**: MVP 阶段是单租户(只服务一个公司)还是多租户?
4. **开源 vs 闭源**: 这套系统的核心模块是否开源?(影响选型)
5. **数据归属**: 会议数据存哪里?(本地 vs 云,影响合规)
