## 〇、口径校准(v1.20, 2026-06-24)

本节是对本文件其余章节的统一校准。遇到不一致时，以本节为准。

### 客户端-服务端架构

VPBuddy 不是纯本地单机系统。它由两部分组成：

- **VP 桌面客户端**：安装在 VP 本地，负责采集系统音频、展示实时生成结果、接收 VP 的 steer 和外发操作。
- **服务端**：部署在 GPU 服务器或私有化环境，负责 ASR、说话人识别、结构化提取、6 类文档生成、Demo 生成、向量检索等重计算任务。

数据流是：客户端采集音频 → 上传服务端解析 → 服务端生成文档和 Demo → 结果实时回传客户端展示。

因此以下表述不准确，不再沿用：
- "完全运行在 VP 自己机器"
- "数据不上传云端"
- "本地 ASR"（ASR 默认在服务端）

可以强调的是：客户端本地安装、会议内容不经过会议平台 SDK、服务端支持私有化部署。

### 实时展示，不是会后初稿

VPBuddy 的核心体验是会议中持续有内容，而不是会议结束后生成初稿。

- 结构化事实（REQ/GOAL/FEAT/RISK/QUE）随转写实时累积、实时展示
- 6 类文档在会议中持续生成、持续更新
- Demo 是实时制作、实时展示的，不是会议结束后才产出

文档、UI 文案、代码注释中如出现"会后生成""会议结束得到初稿"等表述，应改为"会议中实时更新"。

### AI 主动行为边界

AI 可以主动给 VP 展示结论、建议、风险判断和候选方案。只要展示范围仅限 VPBuddy 客户端内部，且最终决策权在 VP，就是允许的。

真正需要禁止的是对外动作：
- 主动外发给客户或外部系统
- 主动触发会议投屏（投屏属于会议软件职责）

因此"AI 不主动推结果"的表述需要修正为：**AI 可以主动在客户端内展示候选结果，但不能主动执行对外动作。**

### VP 自由输入窗口

客户端需要有一个给 VP 自由输入的 Chat 面板。它不是普通客服聊天,而是 VP 控制当前会议智能系统的入口:VP 可以追问、改方向、补充约束、要求某个文档或 Demo 调整。服务端实现必须直接接 Hermes,使用 `meeting:{meeting_id}:vp-chat` 作为主控 session,让 Hermes 负责上下文、工具调用、skill 选择、memory 和 6 个子 agent 调度。

6 个子 agent 继续使用固定 session: `meeting:{meeting_id}:req`、`arch`、`tasks`、`api`、`risk`、`demo`。VP Chat 主控 agent 可以调度它们,但不能创建新的固定交付物类型。Chat 输出只在客户端内展示,并通过 SSE `chat-message` 回流。

## 零、运行时基础(v1.7 新增,v1.18 ADR-0009 落地): VPBuddy = Hermes skill 集合

> **核心架构决策**(v1.7 + 2026-06-21 [ADR-0009](../decisions/0009-部署架构-Hermes-runtime.md) 钉死):VPBuddy 不是自研 LLM 框架,**直接运行在 Hermes Agent 之上**。
> 一个会议 = Hermes 的一个 session;系列会议 = 同一 session 持续;skill 自动生成/复用。
> 目标服务器部署 = `pip install hermes-agent` + `pip install vpbuddy` + `hermes skills install vpbuddy`(5 分钟起)。
> 详见 [ADR-0009](../decisions/0009-部署架构-Hermes-runtime.md)。

### 0.1 映射表

|| VPBuddy 能力 | Hermes 对应能力 | 说明 |
|| --- | --- | --- |
|| 会议 session(单次) | `run_agent.AIAgent(session_id=...)` | 一次会议 = 一个 AIAgent 实例,带完整上下文;按 doc_kind 分 6 个子 session(`meeting:{mid}:{kind}`) |
|| 系列会议 | 同 AIAgent session_id 复用 | 同一 session_id 跨多次对话(hermes 原生支持),上下文自动连续 |
|| 知识库(约束+检索) | `hermes memory` + sqlite-vec | 三类知识(个人/企业/行业)存 hermes memory,跨 session 持久化 |
|| 6 doc_kind 并行 | `ThreadPoolExecutor(max_workers=3)` 调 6 个 AIAgent | controller 一次跑 6 个 in-process AIAgent,真并发 |
|| skill 库 | `skill_manage` | "约束展示"、"steer 解析"、"结构化提取"等都是 hermes skill,可自动生成/复用/版本化 |
|| 工具调用(代码/部署) | `AIAgent(enabled_toolsets=["terminal","file",...])` | AIAgent 进程内调 Hermes native tools,跨进程更快 |
|| 会议时间轴 | `session_search` | 历史会议/上下文可全文检索回放 |
|| 观察性 | Langfuse / OpenTelemetry | hermes 内置集成 |
|| 跨会议连续 | 同 AIAgent session_id 复用 | VP 第二天开会,自动记得昨天的所有内容 |

### 0.2 优势

- ❌ **之前**(v1.6 及更早): LLM 调度、session 管理、skill 系统、记忆系统、工具调用 — **全部要自研**
- ✅ **现在**(v1.7): 全部免费获得,VPBuddy **只做"会议应用层"特色能力**:
  - 客户端音频采集与展示层
  - 实时音/视频处理(ASR 仍可自实现或用第三方)
  - steer 交互 UI
  - 会议特定的 schema(产品说明书/交付物 schema)
### 0.3 关键不变量(2026-06-21 ADR-0009 正式落地,2026-06-22 in-process AIAgent 实现)
- VPBuddy **不**直接调 LLM API(都通过 in-process `run_agent.AIAgent`)
- VPBuddy **不**自己管理 session(都通过 AIAgent `session_id`)
- VPBuddy **不**自己实现 skill 框架(用 hermes `skill_manage`)
- VPBuddy **不**自己实现记忆(用 hermes memory)
- VPBuddy **不**自己实现并发调度(用 `ThreadPoolExecutor(max_workers=3)` 调 6 个 AIAgent)
- VPBuddy **不**自己管理部署包结构(随 hermes 装到 `~/.hermes/skills/vpbuddy/`)
- VPBuddy **是** Hermes 之上的"会议垂直应用"
- 详见 [ADR-0009 §具体落地](../decisions/0009-部署架构-Hermes-runtime.md)

### 0.4 会议 = AIAgent session 的具体含义(2026-06-22 in-process AIAgent 实现)

```
会议开始:
  → 创建/复用 AIAgent(session_id="meeting:{mid}",按 doc_kind 复用 6 个子 session)
  → VPBuddy 加载会议上下文(平台/项目/参会者/知识库选择)
  → 启动后台三轨(累积/生成/steer 接收) - 都是 hermes skill/agent

会议进行中:
  → 后台 skill 持续运行(累积 + 生成)
  → VP 随时 steer(通过 hermes 工具/对话)
  → 跨多个会议(同一 session_id)上下文自动连续

会议结束:
  → 会话状态保留在 AIAgent 实例 + 写文档
  → 可选:生产导出(导出代码 + 推 GitHub)
  → 下次会议:同 session_id 复用 AIAgent,VP 说"接着昨天"即可

代码落地 (src/vpbuddy/sub_session_controller.py):
    from run_agent import AIAgent  # ⚠️ 不是 hermes_agent!
    _AGENT_CACHE: Dict[str, AIAgent] = {}
    
    def _get_or_create_agent(meeting_id, doc_kind):
        sid = f"meeting:{meeting_id}:{doc_kind}"
        if sid not in _AGENT_CACHE:
            _AGENT_CACHE[sid] = AIAgent(session_id=sid, ...)
        return _AGENT_CACHE[sid]  # 同 (mid, kind) 复用同一 AIAgent
```

## 一、定位与设计目标

### 1.1 三句话定位

> **会议 = 人机协同过程**  
> **VPBuddy = 会议中的 AI 协同执行系统**  
> **本架构 = 把"后台并行累积+并行生成"这个抽象落到可运行的工程上**

**核心定位**(v1.3 修正):

> VPBuddy 是**后台会议操作系统**——会议开始时启动,后台**并行做两件事**:
> 1. **累积结构化信息**(客户需求 / 业务目标 / 风险点等)
> 2. **持续生成候选交付物**(Demo / 页面 / 数据模型 / 任务清单 / 工期等)
>
> VP 在会议中**持续 steer(方向盘式引导)**:随时给出方向性输入——『改 X』、『跳过』、『加 Y』——AI 边做边接收,边整合,边继续。  
> **没有『已就绪』概念**——VP 不是在『已完成的成果』上做事,而是在『持续进行的过程』中持续引导。  
> **外发** = VP 任何时候想把当前状态发给客户/团队(VPBuddy 处理);**投屏** = VP 在会议客户端自己点"共享屏幕"按钮(腾讯/飞书/Zoom 都有),**VPBuddy 不参与**——投屏是会议平台的事,不是 VPBuddy 的事。  
> AI 不主动推**结果或决策**(抢话语权);**但**可以主动推**疑问和准备**(为 VP 服务,见 §1.3 修订)。  
>
> 整个系统**无实时性硬约束**: 后台并行任务无延迟目标,VP 主动干预后等 1-3min(人类耐受度)可接受。

### 1.2 设计目标 (按优先级)

| 优先级 | 目标 | 说明 |
| --- | --- | --- |
| P0 | **后台结构化累积** | 会议开始到结束,后台持续累积"客户需求/业务目标/风险点"等结构化数据 |
| P0 | **后台交付物并行生成** | 后台持续从结构化累积中生成候选交付物(Demo/页面/数据模型/任务清单等),VP 任何时候调取都已就绪 |
| P0 | **持续演化** | 交付物不是一次性生成,而是随对话增量更新、回滚、合并(版本树) |
| P0 | **知识库(展示+检索双模式)** | 个人/企业/行业三类知识;**展示模式**(`mode: constraint`)= 后台实时提取/展示,VP 可改但**不阻塞 AI 继续做**;**检索模式**(`mode: retrieval`)= 按需 RAG 检索历史案例 |
| P0 | **人类主导** | VP 主导一切;AI 不主动推结果/不主动外发/不抢话语权(**但**允许:主动问 VP 疑问/主动准备弹药,见 §1.3) |
| P0 | **疑问处理** | AI 持续听,识别模糊/矛盾/未澄清,生成疑问列表(VP 决定看不看) |
| P1 | **预准备内容** | AI 基于会议内容推测可能的提问,提前准备答案/材料(VP 决定用不用) |
| P1 | **VP 持续 steer** | VP 在过程中随时给出方向性引导(改/跳/加/换/参考),AI 实时整合(不阻塞后台工作流);**无延迟目标**,后台持续接收并反映到 demo |
| P1 | **多平台覆盖** | 腾讯会议 / 飞书 / 钉钉 / Zoom,接入层可插拔 |
| P1 | **Sub-agent 并行** | 产品/架构/UI/数据/风险五 Agent 并行推理,而非串行 |
| P2 | **可审计** | 会议时间轴可回放,可追溯"某项决策由谁触发/基于什么累积" |
| P2 | **可移植** | 不绑定单一 LLM/ASR/向量库,核心组件可替换 |
| P2 | **可选生产导出** | VP 显式启用后,会议结束自动转生产代码 + 推 GitHub + 部署测试(非默认,沿用『人类主导』) |

> **关键差异演进**:
> - v1.2 → v1.3: 恢复"**后台交付物并行生成**"为 P0;VP 调取时已经有可投屏的候选交付物
> - v1.5: 约束/背景知识**只展示不阻塞**;约束不注入 system prompt
> - v1.6: **VP 主动干预** → **VP 持续 steer**(范式转变,见 §三/§4.4/§5.1.3)

### 1.3 非目标(明确不做)

- **不是实时辅助工具**(v1.11 修订): VPBuddy 不试图"边听边给结果"或"替 VP 决策";**但**有两个**为 VP 服务**的主动推送是允许的:
  - **疑问窗口**: AI 听不清/有矛盾/需要确认时,**主动问 VP**(VP 决定回不回答)
  - **预准备内容**: 基于会议内容,推测客户可能要问 VP 的问题,**主动准备弹药**(VP 决定用不用)
  - 关键区分:主动推**疑问和准备**(为 VP 服务) ✓;主动推**结果或决策**(抢话语权) ✗
- **不是纯会议录音/纪要工具**: VPBuddy 不只记录信息,核心是**做出交付物**;单纯记录(~~飞书妙记~~ → Superseded by ADR-0008 / 通义听悟)不是它
- **不是通用 Agent 平台**: 不支持任意任务编排,所有能力对齐"会议 → 累积 + 生成 → 干预"主流程
- **不是必须代码 IDE**(v1.7 修订): 默认生成可点击 demo/原型;**可选**生产模式:VP 显式启用后,会议结束自动转生产(导出代码 + 推 GitHub + 部署测试);不是"硬性禁止",也不是"默认自动",由 VP 选择

## 二、五大系统的关系(全景图)

```
                        ┌─────────────────────────────────────┐
                        │  人类决策层(VP / 售前 / 项目负责人)        │
```

**关键关系(与 v1.2 不同)**:
- ③ 交付物生成**不只是反向依赖 ②**,而是**与 ② 并行运行**: ② 累积同时,③ 持续从累积中生成候选交付物
- VP 调取时,③ 已经有可投屏的候选,不需要 VP 触发才开始

### 2.1 五个系统的职责一句话

| # | 系统 | 职责 |
| --- | --- | --- |
| ① | 会议接入层 | 把人/平台/项目/知识库"接进来",**后台持续采集**音/视/文 |
| ② | 会议理解 + Agent | **持续累积**结构化信息;5 Agent 并行推理,后台常驻 |
| ③ | 交付物生成引擎 | **后台持续生成候选交付物**,持续演化;不是 VP 触发才生成 |
| ④ | 指令控制层 | 唯一与 VP 对话的人机接口;把"自然语言指令"翻译为对 ②/③/⑤ 的操作 |
| ⑤ | 统一知识库 | 三类知识;**展示模式**(`mode: constraint`)= 后台实时提取并展示在 Demo/页面/数据模型上,VP 可改但**不阻塞** AI 继续生成;**检索模式**(`mode: retrieval`)= 按需 RAG |

### 2.2 系统之间的约束

- **① 不依赖 ②/③/④/⑤**: 接入层只负责"把信号持续采进来",保持纯净。
- **④ 是唯一对外**: ②/③ 都不直接接收人类指令,所有交互走 ④。
- **⑤ 是横切关注点**: ②/③ 任何累积/生成动作都要经过 ⑤ 校验。
- **② ③ 并行运行**: ② 累积同时 ③ 持续生成;③ 监听 ② 的累积事件触发增量更新,不需要 VP 介入。
- **② 内部自治**: ② 内部的 5 Agent 之间不直接通信,通过共享"累积状态"协同。
- **无实时性约束**: 五大系统都按"能跑就行"的节奏工作,无延迟目标。

### 3.3 版本树(替代交付物生命周期状态机,v1.14 YAGNI)

> **v1.14 修订**:v1.13 之前 §3.3 叫"交付物生命周期状态机",含"后台持续生成 / 已交付 / 撤回 / 归档"4 个状态。**全是过度抽象**——这些"状态"用版本树 + 简单字段就够了,不需要"状态机"概念。删。

```
每个交付物 = 版本树(commit 链)+ 当前 status 字段
                                            ↓
v1.14 之前(过度抽象)              v1.14(简化)
                              ┌────────────────────┐
  后台持续生成 ─→ 已交付       │  状态字段:         │
       ↑↓         ↑↓           │  - generating      │
     撤回       归档           │  - delivered       │
                              │  - archived        │
                              └────────────────────┘
                                            ↓
                              version_tree: [c1, c2, c3, ...]
                              current_commit: c3
                              delivered_commit: c2 (若已交付)
```

**为什么不用状态机**:
- **"已交付"就是 `delivered: bool + delivered_commit: hash` 两个字段** —— 不需要"状态转换规则"
- **"撤回" = `git revert` 在版本树上**(已有) —— 不需要"撤回状态"
- **"归档" = 把旧 commit 标记为 `archived: true`** —— 不需要"归档状态机"
- **状态机 = 过度抽象** —— 普通 JSON 字段比"状态机转换规则"更直观

**关键(v1.14 大幅简化,YAGNI 贯彻到底)**:
- ✅ **没有"投屏中"节点**——投屏是**会议平台原生功能**,不是 VPBuddy 状态(腾讯/飞书/Zoom 都有);v1.10 已删
- ✅ **没有"VP 确认"节点**——所有 VP 动作都是 steer(调方向)/ 外发(发);v1.6 已删
- ✅ **没有"撤回投屏"**——因为 VPBuddy 没有投屏状态,平台有;v1.10 已删
- ✅ **没有"交付物生命周期状态机"**——版本树 + 字段就够;**v1.14 删**
- VP 想跟客户分享时:**VP 在会议客户端点"共享屏幕"**;VPBuddy 不参与投屏(投屏 = 会议平台功能)
- 『后台持续生成』是常态——③ 后台持续生成新版本,旧版本保留形成版本树
- VP steer 在任何时候都有效,直接整合到后台流(不阻塞)
- 外发 = VP 任何时候想把当前状态导出/发送;一旦外发,版本不可变

## 四、模块详细设计

### 4.1 ① 会议接入层(v1.13 双轨 ASR:第一方案默认)

**核心架构(v1.13)**:

| 优先级 | 方案 | 触发条件 | 说话人识别 | 中文 | 成本 |
|---|---|---|---|---|---|
| **P0(默认)** | **第一方案:自接音频流 + Whisper + pyannote** | VP 显式启用,或 MVP 默认 | pyannote-audio 3.1 (80-90%) | ✅ | 服务端 GPU |
| P1 | **第二方案:Zoom RTMS SDK** | VP 用 Zoom 开会 | 平台原生 (95%+) | ⚠️ 英文 | Zoom 付费 |
| P2 | **第三方案:小鱼易连企业版 API** | VP 显式启用(企业版付费) | 平台原生 (95%+) | ✅ | VPBuddy 签企业合作 |
| P3(后处理) | ~~飞书妙记会后校准~~ → ⚠️ **Superseded by ADR-0008 (2026-06-21)** | 不再需要 | ❌ | — |

**关键洞察(v1.13)**:
- ❌ v1.12 默认"平台原生 ASR"看似零成本,但**飞书/腾讯/钉钉的"实时字幕"是客户端 UI,没有开放流式 API 给开发者**——VPBuddy 拿不到会中段段转写,只能等会后
- ✅ 真要"会中实时"只有 3 条路:**(1) 自接音频流 + Whisper,(2) Zoom RTMS,(3) 小鱼易连**
- ✅ 自接音频流 = 中文场景唯一零外部依赖的实时方案
- ✅ ~~飞书妙记 = "会后校准源"~~ → **Superseded by ADR-0008 (2026-06-21)**; 跟 pyannote 结果融合,提高说话人识别准确率 → 改人工/stt_map 填入

**核心组件**

- **平台适配器** (`meeting-adapters/<platform>`): 抽象接口 `MeetingAdapter`,每个平台实现一份
  - 关键接口 `getTranscript()` → 返回带说话人标签的统一 schema(会后,来自平台原生)
  - 关键接口 `getStream()` → 返回音频流(可选,用于自定义分析)
  - 各平台实现:
    - `腾讯会议`: 腾讯会议 AI 小助手 API + SDK
    - `飞书会议`: ~~飞书妙记 API(带说话人)+ 飞书开放平台(会后校准)~~ → **Superseded by ADR-0008 (2026-06-21)**
    - `钉钉会议`: 钉钉智能会议 API + 开放平台
    - `Zoom`: Zoom AI Companion API + Webhook;**或** Zoom RTMS SDK(实时)
- **小鱼易连适配器** (v1.13 新增,可选平台): `XylinkAdapter`
  - 通过小鱼易连 WebSocket push_result 协议接收实时转写段
  - 说话人识别:平台原生(callNumber/dn/callUri/pid/seId)
  - **前置条件**:VPBuddy 团队签小鱼易连企业合作(API 不对个人开放)
- **本地音频采集** (v1.13 新增,第一方案核心): `LocalAudioCapture`
  - **VP 设备 loopback / 麦克风**:
    - macOS: `AVAudioEngine` 输出 tap
    - Windows: WASAPI loopback
    - Linux: PulseAudio monitor source
  - 采集为 PCM 流(16kHz, 16bit, 单声道)
  - **VP 硬约束**:必须用桌面客户端(手机/iPad 不能 loopback)
- **ASR 提供者** (v1.13 新增,第一方案核心): `ASRProvider`
  - 默认:`faster-whisper`(OpenAI Whisper 的 CTranslate2 实现,生产推荐)
  - 备选:OpenAI Whisper API / 讯飞 RTASR(中文付费,¥9.9/小时起)
  - 模型选择:
    - 中文 + 英文混合:`medium`(750M 参数,5.8% WER,CPU 可跑)
    - 仅英文:`large-v3-turbo`(809M 参数,2.7% WER,需要 GPU 加速)
  - **服务端**:VPBuddy 服务器有 GPU(4090/A100);VP 本地只采集音频
- **说话人分离** (v1.13 新增,第一方案核心): `Diarization`
  - 默认:`pyannote-audio 3.1`(开源黄金标准,DER 11-19% benchmark,实际 80-90%)
  - 商业备选:Fireflies.ai(92.8%) / AssemblyAI Universal-2 / Deepgram Nova-3
  - **跨源融合**: ~~会后用飞书妙记 REST 转写(带说话人昵称)校准 pyannote 输出~~ → **Superseded by ADR-0008 (2026-06-21)**;改人工/stt_map 填入
- **统一 schema** (v1.12 既有):
  ```typescript
  interface TranscriptSegment {
    timestamp: number;        // 毫秒(从会议开始计)
    speaker_id: string;       // 平台用户 ID 或声纹 ID(0/1/2)
    speaker_name?: string;     // 平台显示名(VP 可标"我自己"/"客户张总"等)
    text: string;              // 转写文本
    confidence?: number;       // 转写置信度
    language?: string;         // zh-CN / en-US 等
    is_final: boolean;         // true=已确认段;false=临时(可能还会改)
    source: "platform" | "local_capture" | "xylink";  // v1.13 新增:转写来源
  }
  ```
  - 平台不同返回格式不同,`MeetingAdapter` 负责归一化
  - `speaker_name` 缺失时,VP 可手动标注(VP 自己知道谁是谁)
- **工作台初始化**: 加载用户身份/项目/知识库选择,创建"会议 session"
- **后台常驻**: 会议开始后,持续从平台拉取带说话人标签的转写
- **VP 主动选择**(v1.13 新增 UI):会议开始前,VP 选 ASR 方案
  - 默认(第一方案): Whisper 自接,VP 设备 loopback
  - Zoom 客户: 选 RTMS SDK
  - 小鱼易连企业版客户: 选 XylinkAdapter(需 VPBuddy 已签企业合作)
  - 飞书客户 + 不在乎实时性: 选飞书妙记会后处理

**关键决策点**

| 决策 | 推荐 | 理由 |
| --- | --- | --- |
| **第一方案 = Whisper 自接** (v1.13 新增) | 服务端 faster-whisper + pyannote | 中文场景零外部依赖;VP 个人可用;说话人 80-90% 可接受 |
| **说话人识别校准** (v1.13 新增) | pyannote + 飞书 REST 会后转写融合 | 实时 80-90% + 会后 95%+ → 综合 90%+ |
| 屏幕共享捕获 | 平台原生截屏 API | 跨平台一致需要大量适配工作 |
| 缓冲策略 | 内存缓冲 + 定期落盘 | 断电/崩溃时不丢累积成果 |
| 断线重连 | 平台事件驱动,断线后自动重连 | 会议中网络抖动常见 |

**v1.13 修订说明**: v1.12 默认"平台原生 ASR"是错的——飞书/腾讯/钉钉的"实时字幕"是客户端 UI,没有开放流式 API 给开发者,VPBuddy 拿不到会中转写。v1.13 改为**双轨**:第一方案默认 Whisper 自接(实时),平台原生 ASR 降为"会后校准源";**新增小鱼易连作为可选平台**(VPBuddy 签企业合作后启用)。详细调研见 [`docs/research/asr-speaker-diarization-survey.md`](../research/asr-speaker-diarization-survey.md)。

**关键 VP 设备硬约束(v1.13 新增)**:
- ✅ 必须用**桌面客户端**(macOS / Windows / Linux)
- ❌ 手机 / iPad **不能** loopback → VPBuddy 不能用
- ✅ 必须授权 VPBuddy **麦克风/系统音频权限**

**说话人识别双源融合策略(v1.13 新增)**:
```
实时段(Whisper + pyannote):
  speaker_id: 0/1/2 (声纹)
  speaker_name: null
  confidence: 0.7-0.9

会后段(飞书 REST):
  speaker_id: callNumber (飞书用户 ID)
  speaker_name: 张总/李经理 (飞书昵称)
  confidence: 0.95+

VPBuddy 内部合并:
  - 用 callNumber 或声纹 ID 做 key,跨源对齐
  - 给所有段补全 speaker_name
  - 实时段保留声纹 ID,会后段替换为飞书昵称
  - 累积 + 生成使用合并后的统一说话人
```

### 4.2 ② 会议理解 + Agent 系统

**两层结构**

```
[信号流] → 会议理解层 → [累积状态(JSON 对象)] → Agent 推理层 → [更新建议]
              ↑                                            ↓
              └──── 单一可信源(普通 JSON,无状态机) ←───────┘
```

**会议理解层 (单 Agent,持续运行)**

- **ASR 模块**(v1.13 双轨): ~~飞书/腾讯/Zoom 平台原生(会后)~~ → **Superseded by ADR-0008**;只保留 自接音频流 + Whisper + pyannote(实时)
- **多模态融合**: ASR + 屏幕 OCR + 文档解析 → 统一文本流
- **结构化提取**: 从文本流中持续提取"客户需求/业务目标/功能点/风险点/待确认",用 LLM 做带 schema 的 JSON 抽取
- **当前会议结构化状态**(v1.14 改名,以前叫"状态机"): 一个 **JSON 对象**,作为单一可信源(Single Source of Truth),不需要"状态机"概念

**Agent 推理层 (5 Agent 持续并行,v1.16 强化命名)**

> **v1.16 强调**:Agent 名字**固定 5 个**,UI/产品说明书/ADR 全部统一。**禁止改名**(如"风险 Agent"→"合规与审计 Agent")—— 改了破坏心智模型。

| Agent | 关注 | 输出 |
| --- | --- | --- |
| 产品 Agent | 业务目标、用户故事、PRD 风格 | 用户故事 / 业务流程图 / 原型建议 |
| 架构 Agent | 技术选型、模块划分、接口 | 架构图 / 技术栈 / 关键风险 |
| UI Agent | 页面布局、交互流程、视觉 | 页面 wireframe / 组件树 / 交互稿 |
| 数据 Agent | 数据模型、字段、关系、API | ER 图 / API 契约 / 数据流 |
| 风险 Agent | 性能/安全/合规/工期 | 风险清单 / 缓解方案 / 工期估算 |

**Agent 协同机制**

- **不直接通信**: 每个 Agent 独立读"会议状态",独立写"自己的更新建议"
- **冲突解决**: 合并器(主 Agent 或独立服务)按优先级合并:数据 > 架构 > UI > 产品 > 风险
- **共享约束**: 5 Agent 都从 ⑤ 知识库读取约束,但各自有独立的"约束视图"

**关键决策点**

| 决策 | 推荐 | 理由 |
| --- | --- | --- |
| Agent 编排框架 | **in-process AIAgent + ThreadPoolExecutor(3)**(v1.18 落地,2026-06-22) | v1.13 推荐 LangGraph/自研状态机是过度设计;v1.18 真用 in-process `from run_agent import AIAgent(session_id=...)` + ThreadPoolExecutor(max_workers=3) 真并发 |
| Agent 通信 | **共享累积状态(JSON 合并器)** | 比"Agent 间点对点"更可观测、可调试;v1.14 明确不叫"状态机" |
| Agent 数量 | 固定 5 个,**不动态增减**(v1.16 强化) | 5 个:产品/架构/UI/数据/风险;UI/产品说明书/ADR 必须统一用这 5 个名字;改名破坏心智模型 |
| Agent LLM 选型 | **可异构**: 产品/UI 用大模型,数据/风险可用小模型 | 没有延迟约束,可按"质量"而非"速度"选 |

### 4.3 ③ 交付物生成引擎 (后台持续运行)

**v1.3 关键升级**: ③ 不是"VP 触发才生成",而是**后台持续生成**——VP 调取时已经有候选。

**交付物类型**

| 类型 | 形态 | 关键技术 |
| --- | --- | --- |
| **交互 Demo** (核心) | 可点击的 HTML/React 原型 | LLM + 模板 + 组件库 |
| 页面结构 | 页面 wireframe + 组件树 | UI Agent 输出,直接渲染 |
| 功能流程 | 流程图 / 时序图 | Mermaid / PlantUML 渲染 |
| 数据模型 | ER 图 + 字段表 | 数据 Agent 输出 |
| API 设计 | OpenAPI / GraphQL schema | 数据 Agent 输出 |
| 权限模型 | RBAC/ABAC 矩阵 | 风险 Agent + 数据 Agent |
| 开发任务 | 任务卡片列表(含工期) | 风险 Agent + 产品 Agent |
| 工期与里程碑 | 甘特图 / 里程碑表 | 风险 Agent |

**6 项核心交付物清单(v1.16 固定,UI 必须统一显示)**

> **v1.16 锁定**:VPBuddy MVP 阶段**固定 6 项交付物**,UI 必须按此清单显示,**禁止增减**。这跟"5 个 Agent"是平行的硬约束。

| # | 交付物 | 主责 Agent | 关键内容 |
| --- | --- | --- | --- |
| 1 | **交互 Demo** | UI Agent + 产品 Agent | 可点击的 HTML/React 原型,VP 看 demo 的核心 |
| 2 | **需求清单** | 产品 Agent | 编号需求(REQ-001)+ 优先级 + 状态 + 关联客户原话 |
| 3 | **技术架构** | 架构 Agent | 模块图 + 技术选型 + 关键风险标注 |
| 4 | **任务拆解** | 产品 Agent + 风险 Agent | 任务卡片(含工期)+ 依赖关系 |
| 5 | **API 设计** | 数据 Agent | OpenAPI / GraphQL schema + 字段说明 |
| 6 | **风险分析** | 风险 Agent | 风险清单 + 缓解方案 + 合规审计 |

**约束**:
- ✅ UI 必须显示这 6 项(不允许少,不允许多)
- ✅ 主责 Agent 固定(避免混乱)
- ❌ **禁止**改名为"API 设计"→"接口文档"或"风险分析"→"合规与审计"
- ✅ 每项独立运行(并行增量更新,见下"后台持续生成机制")
- ✅ 每项有自己的版本树(commit 链)

**为什么是 6 项**:
- 太少(3 项)覆盖不全(光 Demo 没有数据模型/API/任务,客户问"工期多少"答不上)
- 太多(10+ 项)信息过载,VP 看不过来
- 6 项 = VP 一次会议能 review 的上限(认知研究:7±2 短时记忆容量)

**后台持续生成机制**

- **监听 ② 累积事件**: ② 累积状态变化时,③ 触发对应交付物的增量更新
- **每个交付物独立运行**: Demo/页面/数据模型/任务等可并行生成
- **每个交付物持续演化**: 增量更新产生新 commit,旧 commit 保留形成版本树
- **可中断**: VP 撤回时,正在生成的新版本自动作废
- **可降级**: 某个交付物生成失败不影响其他交付物

**VP steer 的特殊处理**(v1.6 取代『主动触发的特殊处理』)

- VP 的"重生成某交付物"steer → ③ 全量重生成该交付物(基于当前累积状态)
- VP 的"调整某交付物"steer → ③ 局部重生成(基于现有版本 + 调整指令)
- VP 的『投屏/外发』→ **VP 显式动作**(v1.14 改:不再叫"状态机跳转"): VP 在会议客户端点共享屏幕 + VPBuddy 处理导出;任何时候都可触发,无『完成』前提
- VP 的"参考 X" → 触发 ⑤ 检索模式,展示结果,VP 采纳后替换当前展示
- 关键:**所有这些都是 VP 在过程中随时给出的 steer,不是『完成后的干预』**

**关键技术选型**

| 决策 | 推荐 | 理由 |
| --- | --- | --- |
| 文档/数据模型存储 | **JSON + 版本树** | 比 SQLite/Mongo 更轻,适合频繁 diff |
| 交互 Demo 生成 | **沙箱 HTML + React** | VP 在浏览器内可点击,与生产解耦 |
| 渲染管线 | **LLM → 结构化 JSON → 模板渲染** | 避免 LLM 直接生成代码导致不可控 |
| 组件库 | **shadcn/ui 或 Ant Design** | 主流、好维护,符合企业级审美 |

### 4.4 ④ Steer 控制层 (Steer Center,v1.6 改名)

**唯一对外接口**,所有 VP 与 VPBuddy 的交互都走这里。

**核心理念(v1.6)**:
- ❌ 旧:『指令』——意味着 VP 在『下达命令』等 AI 执行
- ✅ 新:『steer』——意味着 VP 在『持续引导方向』,AI 持续做,steer 持续整合

**子模块**

- **steer 解析器**: 把 VP 的自然语言/按钮/手势 steer 解析为对 ②/③/⑤ 的方向性调整
  - 关键词 + LLM few-shot
  - 支持类型(产品说明书 §七): 修改 UI/功能(steer Demo 方向)/ 跳过(steer 任务优先级)/ 加个字段(steer 数据模型)/ 调参考(steer 知识库约束)/ 控制 AI 行为(steer prompt)
  - 关键:解析**方向**,不解析『完成』
- **疑问检测器**(v1.11 新增): AI 持续听,识别需要 VP 澄清/确认的地方
  - 触发类型:① 模糊(客户说"那个系统",没说指哪个) ② 矛盾(客户说"必须 X"但又说"不要 X") ③ 未澄清(客户假设数据库是 PostgreSQL,没明说但也没说不是) ④ 隐含假设(客户说"按惯例做",没说惯例是什么)
  - 紧急度排序: 矛盾 > 未澄清 > 模糊 > 隐含假设
  - VP 交互: 看 / 回答(回答喂回 AI,改善累积) / 关闭 / 标"已知" / 标"不准确"
- **预准备引擎**(v1.11 新增): AI 基于会议内容推测客户/团队可能问 VP 的问题,提前准备弹药
  - 推测依据: 当前累积 + 知识库 + 历史会议相似场景
  - 准备内容类型: 数据(性能/安全/合规) / 方案(架构选型) / 话术(常见反对意见应对) / 风险(工期/成本)
  - VP 交互: 看 / 用 / 不用 / 改写 / 标"不准确"
  - 关键:**不替 VP 回答**——只是准备,VP 决定用不用
- **状态字段**(v1.14 改:不再叫"状态机"): 每个交付物/会议/Agent 都有简单 `status` 字段
  - 值(v1.14 简化):`generating` / `idle` / `delivered` / `archived`(无"投屏中"——投屏是会议平台功能)
  - **steer 整合**:直接更新 `version_tree` 加新 commit,不需要"状态转换"
- **多模态输入**: 不仅文字,还支持:语音/屏幕手势/快捷按钮(会议中打字不方便)
- **多模态反馈**: 屏幕高亮、steer 标识、卡片/按钮
- **权限/审计**: 所有 steer 记录到会议时间轴,可回放

**关键决策点**

| 决策 | 推荐 | 理由 |
| --- | --- | --- |
| 输入形式 | **语音 + 快捷按钮 > 纯文本** | 会议中没空打字,语音/按钮更自然 |
| steer 反馈 | **在被 steer 的元素上实时打标**(小角标『刚才改了 X』) + VPBuddy UI 始终显示当前状态(VP 私下看) | VP 看 demo 都在 VPBuddy UI 上,不需要任何"投屏"动作;跟客户分享时 VP 在会议客户端自己点共享屏幕 |
| steer 历史 | **可回放 + 可撤回** | VP 经常需要『重复 3 分钟前的 steer』或『撤回刚才的 steer』 |
| steer 优先级 | **最近 steer 优先** | 多次 steer 冲突时,后输入的覆盖之前的 |
| 多人协作 | **单 VP 主导,其他成员只读** | 避免多 VP 互相 steer 覆盖 |

### 4.5 ⑤ 统一知识库系统

**三类知识**

| 类型 | 内容 | 来源 | 更新频率 |
| --- | --- | --- | --- |
| **个人** | VP 经验、决策逻辑、方案习惯 | VP 显式输入 / 行为学习 | 低(随 VP 成长) |
| **企业** | PRD/MRD、技术规范、UI 规范、历史项目、SOP | 文档上传 / 知识库对接 | 中(项目演进) |
| **行业** | 行业标准方案、通用架构、竞品方案、最佳实践 | 定期抓取 / 人工编辑 | 高(行业变化) |

**关键定位(v1.5 彻底重写):后台实时展示,VP 可改但不阻塞**

> **v1.5 关键澄清**(用户原话):"应该是提取出约束/背景知识等一切东西,展示,允许 VP 修改但**不强制要求确认**,即**不会停下等待**,后台依然在按照当前约束继续做 demo。另外,约束也**不需要注入 system prompt**。"

**核心原则**(三个明确):
1. **不注入 system prompt**:约束/背景知识是给 VP 看的,不是塞进 LLM 的隐藏 prompt 让它"必须遵守"
2. **实时展示**:Agent 推理时,自动把识别的 constraint 在 Demo/页面/数据模型上**实时标注**
3. **不阻塞 AI**:VP 可以看、可以改、可以问、可以批复——但 AI **不等待 VP 反馈**,继续按当前约束做 demo

每条知识带 `mode` 字段,标识用途:

| mode | 展示位置 | 典型内容 | VP 行为 | AI 行为 |
| --- | --- | --- | --- | --- |
| `constraint` | Demo/页面/数据模型上**实时标注来源** | 规则/SOP/规范/UI 规范/技术栈限制/编码标准 | **可看、可改、可问、可批复**,不强制确认 | **不等待**,继续按当前约束生成 |
| `retrieval` | 侧栏弹窗列出 Top-k 检索结果,带来源链接 | 历史项目/案例/客户文档/外部资料 | 点"采纳"→ 替换当前 constraint;或忽略 | 检索失败不阻塞主流程 |

**展示模式工作流**(`mode: constraint`):
- Agent 推理时识别"这个设计用到了约束 X"
- 在 Demo 元素上挂载一个**可点击的来源标签**(右上角小角标)
- VP 点开看详情:"这个按钮用 #1890ff 因为企业 UI 规范 §3.2 规定"
- VP 改改 → 改动立即反映到 demo 元素;但 **AI 此时不一定重新生成**(版本树记录)
- VP 主动调取时才触发全量重生成

**检索模式工作流**(`mode: retrieval`):
- VP 问"参考下历史项目 X"或 Agent 遇到全新场景
- 侧栏弹出 Top-k 检索结果(标题+摘要+置信度+来源)
- VP 点"采纳"→ 检索内容**替换**当前 constraint,后续 AI 生成按新约束走
- VP 不采纳 → AI 继续用现有约束,不阻塞

**两类内容的边界**:
- 一份规范文档**通常同时含两种模式**:
  - 规则部分(`mode: constraint`)→ 在 demo 上展示
  - 案例部分(`mode: retrieval`)→ VP 按需检索
- 元数据示例:
  ```
  knowledge:
    title: "本企业 UI 规范 v2.1"
    sections:
      - title: "主色 #1890ff、辅色 #52c41a"
        mode: constraint        # 展示在 demo 元素上
        priority: high
        scope: [ui_agent, frontend_agent]
      - title: "按钮圆角案例 5 个"
        mode: retrieval         # VP 按需检索
        scope: [ui_agent]
  ```

**知识图谱结构**

```
个人 ─┐
     ├─→ 约束集 ─→ Agent 累积/生成 ─→ 交付物
企业 ─┤
行业 ─┘
```

每条知识带元数据:
- `scope`: 适用 Agent(产品/架构/UI/数据/风险/all)
- `priority`: 优先级(强制/建议/可选)
- `version`: 版本号(随时间更新)
- `confidence`: 置信度(影响是否覆盖 Agent 自身判断)

**关键决策点**

| 决策 | 推荐 | 理由 |
| --- | --- | --- |
| 知识存储 | **向量库 + 关系库双写** | 向量用于相似度,关系用于"继承/冲突" |
| 向量库选型 | **pgvector / Milvus / Qdrant** | 视部署规模,小团队 pgvector 够用 |
| 知识更新 | **PR 模式**(知识也是代码) | 重要知识需要审核,避免污染 |
| 行业知识抓取 | **人工编辑 + 定期审核** | 自动抓取质量不可控 |

## 五、关键机制(架构级)

### 5.1 后台并行运行机制

**v1.3 升级**: 不再是"持续累积+主动响应"双轨,而是"**后台并行三轨**"。

#### 5.1.1 后台结构化累积(无延迟目标)

- **持续运行**: 会议开始启动,会议结束停止;不卡延迟,能跑就行
- **增量累积**: 每次新输入增量更新结构化状态,不去重历史
- **定期落盘**: 内存累积 + 定期写入持久化存储,断电/崩溃时不丢
- **资源节制**: 闲时降频(1-2s 一次处理),忙时升频;不抢占 VP 设备的 CPU/内存
- **后台观察**: 关键指标(累积条目数、提取覆盖率、模型费用)实时记录,可查

#### 5.1.2 后台交付物并行生成(无延迟目标)

- **监听 ② 累积事件**: 累积状态变化时自动触发对应交付物的增量更新
- **每个交付物独立运行**: Demo/页面/数据模型/任务等可并行生成,互不阻塞
- **增量生成**: 基于现有版本 + 累积 diff,而不是全量重生成
- **版本树**: 每次更新产生新 commit,旧 commit 保留
- **可降级**: 某交付物生成失败不影响其他交付物
- **资源节制**: 与 ② 累积协调 CPU/内存使用,避免抢占

#### 5.1.3 VP steer 流(v1.6 取代 『VP 主动干预』;v1.8 加 session 生命周期,**v1.9 删掉**)

> **核心理念**: VP steer 是**方向性输入**,不是『任务』。
> AI 后台持续工作,steer 持续整合到工作流中,没有『完成任务』概念。
>
> **(v1.9 修订)**: 之前 v1.8 加的"session 生命周期感知"是过度设计,删掉。如果实际遇到 hermes session 状态相关的 bug,再加回来。

- **持续接收**: VP 任何时候的 steer 都被立即接收,无队列等待
- **实时整合**: steer 直接进入当前 ②/③ 工作流,被影响的元素**立即反映**到 demo
- **不阻塞**: steer 整合过程中,后台其他工作流继续运行
- **可视化反馈**: 被 steer 的元素打标『刚才改了 X』,让 VP 知道 steer 已生效
- **可撤回**: VP 可以『撤回刚才的 steer』,回到 steer 前的状态
- **可累积**: 多个 steer 累积,后输入覆盖前输入(同 scope)

#### 5.1.4 疑问处理(v1.11 新增)

> **核心理念**: AI 主动问 VP"我没听清/有矛盾/需要确认"是**为 VP 服务**,不抢话语权。

- **持续检测**: AI 后台持续听,识别疑问触发类型(模糊/矛盾/未澄清/隐含假设)
- **紧急度排序**: 矛盾 > 未澄清 > 模糊 > 隐含假设
- **UI 展示**: VPBuddy 左侧/右侧**固定窗口**显示疑问列表(按紧急度排序)
- **VP 交互**:
  - 点击看上下文(显示"AI 听到的原始对话片段")
  - 在窗口直接回答(回答**自动喂回 AI**,改善累积状态)
  - 关闭/标"已知"(避免重复)
  - 标"不准确"(反馈 AI,避免再生成此类疑问)
- **频率控制**: 避免疑问太多刷屏(默认 1-2 分钟最多 1 个新疑问)
- **去重**: 同一疑问不重复生成(用 fingerprint 匹配)

#### 5.1.5 预准备内容(v1.11 新增)

> **核心理念**: AI 主动为 VP 准备"客户可能要问的问题 + 答案",VP 决定用不用。

- **推测来源**: 当前累积内容 + 知识库 + 历史相似会议场景
- **准备类型**:
  - 数据类: 性能/安全/合规/规模 数据
  - 方案类: 架构选型/技术栈/部署方案
  - 话术类: 常见反对意见的应对
  - 风险类: 工期/成本/技术债
- **UI 展示**: 疑问窗口**旁边**的"预准备"窗口(区分清楚,不要混淆)
- **VP 交互**:
  - 看完整准备材料
  - 用(把内容复制到聊天/外发)
  - 不用(关闭即可,不强制)
  - 改写(在窗口里编辑)
  - 标"不准确"(反馈 AI)
- **频率控制**: 跟疑问类似,避免过多
- **不替 VP 回答**: 准备内容**不自动出现在会议对话中**;只在 VPBuddy UI 内部

#### 5.1.4 通用保障

- **背压控制**: 累积过快时,合并多次输入再处理,避免雪崩
- **可解释性**: 任何"任务执行中"必须告诉 VP 当前在做什么(等 ASR? 等 LLM? 等渲染?)
- **错误恢复**: 任何单点故障不丢失累积状态;有重连/重试机制

### 5.2 Sub-agent 并行推理

- **任务队列**: 5 Agent 共享一个"累积状态变化"事件流
- **独立沙箱**: 每个 Agent 自己的 LLM 上下文,不互相污染
- **合并策略**: 见 4.2 冲突解决
- **观察性**: 每个 Agent 的输入/输出/耗时/费用都记录

### 5.3 交付物持续演化

- **不是"覆盖"**: 每次更新产生新 commit,旧 commit 保留
- **可回溯**: VP 随时"回到 5 分钟前的版本"
- **可对比**: 两个版本 diff 可视化
- **可合并**: 多个并行草拟可手动合并
- **可并行生成**: 多个交付物可同时增量更新,互不阻塞

#### 5.4.1 展示模式 (`mode: constraint`)

> **v1.5 澄清**: constraint 模式 = **后台实时提取并展示**,**不注入 system prompt**,**不阻塞 AI 继续做 demo**。

- **提取**: Agent 推理时**后台自动识别** applicable constraint(规则/SOP/规范/历史习惯)
- **展示**: 在 Demo/页面/数据模型上**实时标注**来源(右上角小角标/UI 标签/数据模型注释)
- **VP 交互**: 可以**看、改、问、批复**,**不强制确认**
- **不阻塞**: AI **不等待 VP 反馈**,继续按当前 constraint 生成 demo
- **优先级**: 由 knowledge.priority 字段控制(mandatory / recommended / optional)
- **版本**: constraint 更新时**不静默覆盖**,保留历史(版本树)
- **可解释**: 每个设计元素都带"来源"标签,VP 可追溯/why/why not
- **不注入 system prompt**:constraint 只展示给 VP 看,**不**塞进 LLM 的隐藏指令让 LLM "必须遵守"——LLM 按自己的理解生成,VP 通过 demo 的展示来"管理"约束

#### 5.4.2 检索模式 (`mode: retrieval`)

- **触发**: 
  - VP 显式问"我们做过类似项目吗"、"参考下历史项目 X"
  - Agent 遇到全新场景(没有 constraint 可循)
- **检索路径**: 向量相似度 + 元数据过滤(scope / project / tag)
- **展示**: 侧栏弹窗列出 Top-k 检索结果,带来源链接
- **采纳**: VP 点击"采纳"后,检索内容**替换当前 constraint**
- **防淹没机制**:
  - top-k 限制(默认 5)
  - 单条长度限制(默认 500 token)
  - relevance 阈值(默认 ≥ 0.7)
  - 总长度限制(retrieval 部分 ≤ 30% context window)
### 5.5 会议时间轴(需求演化)

**不是日志**,是"需求如何被构建为系统"的过程。

- 每个时间点: `t 时刻, 客户说 X → 累积到 Y → 触发 ③ 生成 Z`
- 可视化: 时间线 + 树形分支(回滚/并行)
- 检索: 按"功能/风险/决策"分类浏览
- 用途: 复盘 / 客户确认 / 团队交接

### 6.1 由 Hermes 提供(不需要 VPBuddy 自研)

| 能力 | Hermes 机制 | VPBuddy 用法 |
| --- | --- | --- |
| Session 管理 | `hermes session` | 一个会议 = 一个 session;系列会议 = 同一 session |
| Skill 框架 | `skill_manage`(create/patch/edit) | VPBuddy 的核心能力(约束展示/steer 解析/5 Agent)都是 hermes skill |
| Memory | `hermes memory` + 向量库 | 三类知识 + 会议结构化状态都存 hermes memory |
| Sub-agent 并行 | `ThreadPoolExecutor(3)` + in-process AIAgent(session_id=...) | 6 doc_kind 真并发;同 (mid, kind) 复用 AIAgent 实例 → 真 session 持久化 |
| 工具调用 | `native tools` / `MCP` | 平台 SDK 接入(腾讯/飞书等)用 MCP |
| 历史回放 | `session_search` | 会议时间轴 = session_search |
| 定时任务 | `cronjob` | 会议外的衍生任务(发提醒/同步状态)用 cronjob |
| 跨平台 | MCP 统一接口 | 不需要 VPBuddy 单独适配每家 LLM |
