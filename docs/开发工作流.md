## 2. 两套环境

| 环境 | 地址 | 用途 |
|------|------|------|
| **公网 GPU server** | `47.100.182.3:28765` (内网 `8765`) | ASR、文档生成、KB 检索、LLM 调用 |
| **本机 (开发机)** | Windows, Node.js | 前端开发、单元测试、Playwright E2E |

### 2.1 不需要 GPU 的操作

- 服务端 Python 单元测试（运行在本地 TestServer）
- 前端构建（Vite）
- 大多数 Playwright UI 测试
- Rust 音频单元测试（`audio_unit`）

### 2.2 必须走 GPU 服务器的操作

- 任何涉及 KB (Chroma) 的测试
- 任何涉及 ASR / 上传音频 的测试
- 文档生成端到端测试
- Rust E2E 测试 `gpu_e2e`

测试代码中通过 `gpu_server` fixture 来获取 GPU 地址：

```python
# src/tests/e2e/conftest.py
GPU_SERVER_URL = os.environ.get("VP_E2E_GPU_URL", "http://47.100.182.3:28765")
```

## 3. 服务端测试

### 3.1 环境准备

```bash
pip install -e ".[dev]"
```

### 3.2 运行单元测试（本机，不需 GPU）

```bash
# 运行全部单元测试（约 136 个）
python -m pytest src/tests/ --tb=short -q

# 排除 E2E（默认行为）
python -m pytest src/tests/ --tb=short -q --ignore=src/tests/e2e

# 运行特定测试文件
python -m pytest src/tests/test_task_manager.py --tb=short -v
python -m pytest src/tests/test_experience.py --tb=short -v
python -m pytest src/tests/test_kb_search_tool.py --tb=short -v

# 不跳过 E2E 中的"预存失败"（如 CORS 不带 Origin header）
# 该测试需要带 Origin header 才正确，见 §9
```

所有测试在 `conftest.py` 中会自动设置 `HF_HUB_OFFLINE=1` / `TRANSFORMERS_OFFLINE=1`，防止 embedding 模型下载卡死。

### 3.3 运行 E2E 测试（需要 GPU server）

```bash
# 设置 E2E 标志
$env:RUN_E2E=1

# 测试 GPU 路由覆盖（28+ 端点）
python -m pytest src/tests/e2e/test_fastapi_server.py --tb=short -v

# 测试全流程文档生成（上传→ASR→6 文档）
python -m pytest src/tests/e2e/test_full_e2e_docs_generation.py -m e2e -v

# 测试边界情况
python -m pytest src/tests/e2e/test_edge_cases.py -m e2e -v

# 运行所有 E2E 测试
python -m pytest src/tests/e2e/ -m e2e --tb=short
```

**E2E 测试架构**（铁律 5：真实部署驱动）：

```
本机 (pytest)                    GPU server (47.100.182.3:28765)
┌─────────────────┐             ┌──────────────────┐
│  Vite preview    │             │  vpbuddy ui      │
│  port 4173       │  fetch ──→ │  /api/*           │
│  (client dist)   │  ←── resp  │                   │
├─────────────────┤             ├──────────────────┤
│  Playwright      │  JS 注入    │  真实 ASR         │
│  headless        │  __TAURI__ │  真实 LLM         │
│  Chromium        │  stub      │  真实 Chroma      │
└─────────────────┘             └──────────────────┘
```

### 3.4 E2E 关键 fixture

| fixture | 作用域 | 说明 |
|---------|--------|------|
| `gpu_server` | session | 验证 GPU 可达，返回 base URL |
| `synth_wav` | session | 30s 合成语音 |
| `short_wav` | session | 8s 短音频 |
| `vite_preview_url` | session | 启动 `vite preview` 提供前端 |
| `playwright_browser` | session | Playwright headless Chromium |
| `page` | function | 注入 Tauri stub |
| `page_with_gpu` | function | Tauri stub + 真 GPU URL |

### 3.5 直接打 GPU 路由测试

当 Python TestServer 不方便时（如测 GPU 独占功能），可以直接用 `urllib` 写独立脚本测试 GPU 服务器：

```python
GPU = "http://47.100.182.3:28765"
# GET / POST / OPTIONS 请求同上，不需要 fixture
```

## 4. 桌面客户端构建

### 4.1 通过 GitHub CI 构建（推荐）

修改客户端代码后，push 到 `main` 分支即可触发自动构建。

**触发方式**（任选一）：
1. push 到 `main` 且路径包含 `vpbuddy-client/**` 或 `.github/workflows/tauri-multi-build.yml`
2. 在 GitHub Actions 页面手动触发 (workflow_dispatch)
3. push tag `v*`

**CI Job 产出**：

| Job | Runner | 产出 | 下载位置 |
|-----|--------|------|---------|
| `test` | ubuntu-24.04 | cargo check + test | — |
| `build-linux` | ubuntu-24.04 | `.deb` | Action Artifacts |
| `build-macos` | macos-14 | `.app.zip` + `.dmg` | Action Artifacts |
| `build-windows` | windows-2022 | `.exe` (NSIS) | Action Artifacts |
| `release` | ubuntu-24.04 | GitHub Release | (仅 tag push) |

**CI 工作流文件**：`.github/workflows/tauri-multi-build.yml`

### 4.2 客户端版本号统一

客户端版本号在三个地方保持一致（均为 `0.9.0`）：
- `vpbuddy-client/package.json` → `version`
- `vpbuddy-client/src-tauri/Cargo.toml` → `[package] version`
- `vpbuddy-client/src-tauri/tauri.conf.json` → `version`

### 4.3 本地前端开发（不需构建完整 Tauri）

```bash
cd vpbuddy-client
npm install
npm run dev          # Vite dev server, port 1420
npm run build        # 构建前端到 dist/
npm run preview      # preview dist/, port 4173
```

本地前端开发时，通过 `page` fixture 注入的 `window.__TAURI__` stub 模拟 Rust 端，所有 API 调用直接走 `fetch` 到 GPU server。

## 8. 部署到 GPU 服务器

### 8.1 服务端代码更新

GPU 服务器在公网 `47.100.182.3`，通过 SSH (`port 16159`) 访问。

**方式 A：SFTP 上传（紧急修复）**

```python
# 从本机 SFTP 上传改动的文件
import paramiko
client = paramiko.SSHClient()
client.connect("47.100.182.3", port=16159, username="root", password="...")
sftp = client.open_sftp()
with sftp.open("/data/vpbuddy/server/src/vpbuddy/scripts/gpu_transcribe.py", "wb") as f:
    f.write(open("src/vpbuddy/scripts/gpu_transcribe.py", "rb").read())
sftp.close()
# 重启 UI
client.exec_command("pkill -f 'vpbuddy ui'; sleep 2")
client.exec_command("export HF_ENDPOINT=https://hf-mirror.com; cd /data/vpbuddy/server && nohup /data/vpbuddy/venv/bin/vpbuddy ui --port 8765 > logs/ui.log 2>&1 &")
```

**方式 B：Git pull（源码同步）**

1. 在本机 push 到 GitHub
2. 在 GPU 上 `cd /data/vpbuddy/server && git pull origin main`
3. 重启 `vpbuddy ui`

### 8.2 环境变量

| 变量 | 值 | 说明 |
|------|----|------|
| `HF_ENDPOINT` | `https://hf-mirror.com` | HuggingFace 镜像 |
| `HF_HUB_OFFLINE` | `1` | 离线模式 |
| `TRANSFORMERS_OFFLINE` | `1` | 离线模式 |
| `VPBUDDY_DOCS_DIR` | `/home/zsd/vpbuddy/docs` | 文档输出目录 |
| `VPBUDDY_DATA_DIR` | `/home/zsd/vpbuddy/data/meetings` | 会议数据目录 |
| `VPBUDDY_POLL_INTERVAL` | 可选 | 轮询间隔 |

### 8.3 启动/停止

```bash
# 启动 UI (GPU 服务器上)
export HF_ENDPOINT=https://hf-mirror.com
cd /data/vpbuddy/server
nohup /data/vpbuddy/venv/bin/vpbuddy ui --port 8765 > logs/ui.log 2>&1 &

# 停止
pkill -f 'vpbuddy ui'

# 验证
curl http://localhost:8765/api/status
```

## 9. 已知陷阱

### 9.1 CORS 头测试

`test_cors_headers` 测试必须带 `Origin` header 才能通过，因为 CORSMiddleware 只在请求有 Origin 时回复 `Access-Control-Allow-Origin`。普通 `urllib` GET 不带 Origin，所以测试需要：

```python
_, _, headers = _http_get(url, extra_headers={"Origin": "http://localhost:1420"})
```

### 9.2 Embedding 模型缓存

GPU 上 `paraphrase-multilingual-MiniLM-L12-v2` 缓存可能不完整（缺 `pytorch_model.bin`）。修复方法：

```bash
# 在 GPU 上运行
python -c "
import os; os.environ['HF_ENDPOINT'] = 'https://hf-mirror.com'
from huggingface_hub import hf_hub_download, snapshot_download
# 删除残缓存后重新下载
snapshot_download('sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2')
"
```

### 9.3 `threading` import 缺失

`gpu_transcribe.py` 中 `_ASR_CACHE_LOCK = threading.Lock()` 要求 `import threading`。漏了会导致 `upload_audio` 路由返回 500：

> `"error": "name 'threading' is not defined"`

### 9.4 客户端 `banner` ReferenceError

`main.js` 中 `renderAudioDevices()` 如果忘记 `const banner = document.getElementById("audio-warning")`，JavaScript 会抛 `ReferenceError: banner is not defined`，被 `initAudioDevices` 的 catch 捕获显示在 UI 上。

### 9.5 本地 `index.lock`

本机 `.git/index.lock` 可能卡住（安全工具禁止删除）。解决方法：在临时目录 clone 一份新仓库。

```bash
cd /path/to/temp
git clone https://github.com/zhangsheng377/vpbuddy.git vpbuddy-tmp
# 复制改动文件
cp /path/to/changed/file vpbuddy-tmp/src/vpbuddy/...
# commit + push
cd vpbuddy-tmp
git add .
git commit -m "..."
git push origin main
```

### 9.6 E2E 测试 skip 标记

所有 E2E 测试都有 `@pytest.mark.e2e` 标记。不带 `RUN_E2E=1` 时自动跳过。测试前必须：

```bash
$env:RUN_E2E=1
```

### 9.7 Windows 客户端构建

本机没有 Rust toolchain 时，不能本地构建 Windows 客户端。必须通过 push → GitHub Actions CI 自动构建。

### 9.8 GPU 服务器跑的不是最新代码

这是最容易反复踩的坑。**GPU 上的 Python 包是以 editable mode 安装的**（`pip install -e .`），所以：

- 改 `src/vpbuddy/` 下的文件 → 服务器 VM 内的 `vpbuddy` 模块立即生效，不用 pip install
- **但** GPU 服务器有自己的 Git 分支，不会自动 pull 你的 push

**典型症状**：本机修了 bug 并 push 到 GitHub，E2E 测试还报同一个错 → 说明 GPU 跑的还是旧代码。

**排查方法**：在 GPU 上确认当前运行的源码

```bash
# 确认模块加载路径
/data/vpbuddy/venv/bin/python3 -c "
import vpbuddy.sub_session_controller
print(vpbuddy.sub_session_controller.__file__)
# 检查关键行
lines = open(vpbuddy.sub_session_controller.__file__).readlines()
for i, l in enumerate(lines):
    if 'model=' in l:
        print(f'  line {i+1}: {l.rstrip()}')
"
```

**正确的部署流程**（选一）：

| 方式 | 命令 | 适用场景 |
|------|------|---------|
| A. SFTP 上传 | `sftp.put(local_path, remote_path)` → 重启 | 紧急修复，改单文件 |
| B. Git pull | `ssh ... git pull origin main` → 重启 | 批量改动后同步 |
| C. 可编辑安装 | `pip install -e .` → 需要时重新跑 | 安装新依赖时 |

**一定要验证**：上传后确认 GPU 上的文件确实包含你的修改：

```bash
# 在 GPU 上检查
grep '关键代码' /data/vpbuddy/server/src/vpbuddy/your_file.py
```
